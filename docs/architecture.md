# 시스템 아키텍처

[SVG 원본](architecture.svg) · [PNG](architecture.png)

## 현재 구현된 초기 설정

- FastAPI의 생존 점검과 PostgreSQL·Redis 연결 점검
- SQLAlchemy 연결·Alembic migration 환경(업무 테이블 없음)
- Redis broker·Celery 단일 동시 실행 워커·진단 작업
- Docker Compose와 GitHub Actions 기반 검사

다이어그램 실선은 현재 연결 점검 가능한 구성이다. 점선은 이후 연결할 제품 기능이며, 운영 인프라가 이미 배포됐다는 뜻이 아니다.

## 목표 흐름 — 아직 미구현

1. 브라우저가 API에서 서명 URL을 받아 객체 저장소에 업로드한다.
2. API가 PostgreSQL에 작업을 기록하고 Redis에 작업 ID를 전달한다.
3. 워커가 음성·영상·텍스트를 분석하고 특징과 버전별 점수를 저장한다.
4. 사용자가 후보와 자막을 수정한다.
5. 워커가 선택한 편집 버전을 FFmpeg로 렌더링하고 저장소에 업로드한다.
6. 사용자가 짧은 유효기간의 URL로 결과를 내려받는다. SNS 연결은 후속 범위다.

현재 API에는 이 흐름의 endpoint가 없다. 진단 작업은 영상 처리 없이 워커가 메시지를 소비하는지만 확인한다.

## 선정 이유

- FastAPI: Python 분석 모듈과 HTTP 경계를 분리하면서 같은 저장소에서 개발.
- PostgreSQL: 관계형 프로젝트·편집 이력과 JSONB 분석 메타데이터를 함께 관리할 계획. MySQL도 가능.
- Redis: 작은 작업 메시지 전달과 초기 구성의 단순함. RabbitMQ도 대안이며 장기 작업·내구성 설정을 별도로 검토해야 함.
- Celery: Python 작업의 실행·동시성·향후 대기열 분리. exactly-once 보장 없음.
- 객체 저장소: API와 워커의 로컬 디스크에 종속되지 않는 파일 공유. 이번 단계에서는 미연결.

## 초기 배포와 확장

로컬 Compose는 API·워커·Redis·PostgreSQL을 한 개발 환경에 둔다. 사용자 공개 단계에서는 관리형 PostgreSQL·객체 저장소, API/워커 CPU·메모리 격리, 인증, TLS, 백업·복구를 마련한다. 처리 대기 시간이 증가하면 워커부터 별도 호스트로 옮긴다. GPU는 필요한 분석 단계에만 추가한다. Kubernetes·Kafka는 초기 범위에 포함하지 않는다.

## 구현 전에 결정할 복구·비용 조건

- DB 기록과 broker 발행 사이 실패를 outbox 또는 재전달 점검으로 해결
- 작업 ID·편집 버전을 기반으로 중복 실행과 결과 덮어쓰기 방지
- 작업 시간 제한, 재시도 횟수, 워커 중단 후 상태 복구
- 사용자별 분량·동시성·비용 한도와 파일 보존 기간
- 분석 결과 재사용과 선택한 후보만 최종 렌더링

현재 Celery 제한값 240/300초와 Redis 재전달 시간 600초는 짧은 진단 기반의 초기 설정이다. 실제 영상 길이·작업 단계 측정 없이 운영 기본값으로 사용하지 않는다. 기본 조기 ACK를 사용하며 업무 작업의 장애 복구를 보장하지 않는다.

## 참고 디자인

사용자가 제공한 SVG의 흰 배경, 분홍 그라데이션 제목, 점선 바깥 경계, 보라·초록·청록 영역, 주황 카드, 직각 연결선 구성을 참고했다. 원본 SVG·개인 경로·참고 자료는 저장소에 포함하지 않았다. 특정 클라우드에 배포되지 않았으므로 AWS VPC·EC2 등의 실제 배포 표시는 사용하지 않았다.
