# 개발 환경 점검과 장애 대응

> 장애가 나면 API·DB·Redis·워커 중 어디서 멈췄는지 먼저 구분합니다. 증상별 확인 순서와 자료를 보존하는 정리 방법, 수동 중단 처리의 조건을 안내합니다.

장애가 나면 API·DB·Redis·워커 중 어디에서 멈췄는지 먼저 구분한다. 상태 조회 오류를 업무 실패로 확정하거나 실행 중인 작업을 다시 보내지 말고, 아래 순서로 증거를 확인한다.


## 기본 확인 순서

1. `docker info`로 Docker Linux 엔진을 확인한다.
2. `docker compose ps`로 컨테이너 상태를 확인한다.
3. `/health/live`와 `/health/ready`를 구분해 호출한다.
4. `docker compose logs --tail=100 api worker postgres redis`로 해당 시간의 로그를 본다.
5. 수정 후 같은 점검과 필요한 통합 검사를 다시 수행한다.

## 증상별 대응

| 증상 | 의미·가능 원인 | 확인과 조치 |
|---|---|---|
| Docker 연결 실패 | Docker Desktop Linux 엔진 중단 | 엔진 시작 후 재확인 |
| 8000·5432·6379 바인딩 실패 | 기존 로컬 서비스와 포트 충돌 | 사용 프로세스 확인, 호스트 포트·로컬 URL 함께 조정 |
| live는 200, ready는 503 | DB 또는 Redis 연결 실패 | checks 응답과 컨테이너 로그 확인 |
| ready는 200, 진단 timeout | 워커 미실행·다른 대기열·결과 backend 없는 워커가 소비 | 워커 로그·대기열·진단 실행 명령 확인 |
| ModuleNotFoundError: app | 루트 밖 실행·다른 Python 환경 | 루트에서 uv 명령 사용, pytest pythonpath 설정 확인 |
| Redis 메모리 관련 발행 실패 | noeviction 제한 도달 | 누적 메시지·메모리 확인, 원인 해결 전 무한 재시도 금지 |
| 컨테이너 unhealthy | 준비 점검 실패 | unhealthy 표시 자체가 자동 복구를 의미하지 않음 |

## 데이터와 정리

일반 종료는 `docker compose down`이다. 데이터 볼륨은 유지한다. 원인 확인 없이 볼륨 삭제·DB 초기화·대기열 전체 비우기를 복구 수단으로 사용하지 않는다.

진단 테스트는 `shortform-diagnostic-worker`라는 임시 컨테이너와 결과 키를 사용할 수 있다. 테스트가 중단됐다면 해당 컨테이너인지 확인한 뒤 중지·제거한다. 일반 업무 환경에 이 점검 절차를 그대로 적용하지 않는다.

## 현재 복구의 한계

기존 개발 환경 복구 때 두 포트 모두 생존 점검은 200이었지만 준비 점검은 503이었습니다. 호스트의 남은 디스크 공간이 수 MB였고 Docker 상태 조회도 시간 안에 끝나지 않았습니다. 당시에는 백업 검증과 엔진 응답 전에 마이그레이션을 진행하지 않았습니다. 복구 뒤 API·워커 코드와 DB 스키마 버전을 맞추고 백업 대비 기존 테이블 19개와 원본·편집 이력을 대조했습니다. 같은 증상이면 엔진 상태와 디스크부터 확인하고 기존 자료의 백업·복원 가능성을 확인하세요. [당시 중단과 복구 기록](../05-development/harness/records/2026-11-18-flow-runtime.md)

조기 ACK는 워커가 메시지를 일찍 수신 확인한다는 뜻입니다. 워커를 다시 시작해도 수신 확인한 작업은 자동 복원되지 않습니다.

## 장애 기록 항목

시각(UTC 저장·필요 시 KST 표시), 커밋, 서비스, 수행 명령, 비밀값을 제거한 오류, 영향, 조치, 재검증 결과를 남긴다. 원본 영상·접속 문자열을 공개 이슈나 로그에 붙이지 않는다.

## 비동기 작업이 멈춘 경우
