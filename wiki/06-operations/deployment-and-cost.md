# 배포·확장·비용 설계

> 현재 로컬 구성을 공개 운영 환경으로 옮기려면 자원·저장·비용 제한을 함께 정해야 합니다. 배포 후보와 확장 판단, 아직 결정하지 않은 예산·운영 조건을 정리합니다.

[위키 홈](../README.md) · [카테고리 목차](README.md)


## 현재와 목표 구분

현재는 Compose 로컬 개발 구성만 있다. 인터넷 공개 서비스·관리형 DB·객체 저장소·GPU·자동 배포는 없다. GitHub 레포가 공개되어 있다는 사실과 서비스 공개는 다르다.

## 초기 공개 배포 후보

API·워커·브로커를 작은 CPU 서버에서 시작하고 DB와 영상 파일은 관리형 저장소를 검토한다. 워커의 CPU·메모리·인코딩 스레드를 제한해 API 응답에 주는 영향을 줄인다. 실제 서버 크기는 샘플 처리 측정 후 정한다.

현재 Compose의 서비스별 메모리 제한은 로컬 개발을 위한 설정이다. 실제 값은 [Compose 원본](../../compose.yaml)을 확인한다. 실제 영상 모델을 담을 수 있는 운영 사양으로 간주하지 않는다. 워커 한 대와 Redis 한 대는 고가용성 구성이 아니다.

## 확장 판단

| 관측 증상 | 먼저 확인 | 다음 조치 후보 |
|---|---|---|
| 처리 중 API 지연 | CPU·메모리 경합 | 워커 별도 호스트 |
| 긴 작업 대기 | 처리 시간·동시성·API 제한 | 워커 증설·분석/출력 대기열 분리 |
| 모델 추론 비용 증가 | 분량·호출 단가·사용률 | 일부 단계만 GPU 또는 다른 제공자 |
| DB 지연 | 쿼리·인덱스·연결 수 | 최적화 후 용량 조정 |
| 저장량 증가 | 원본·임시 파일 누적 | 보존 정책·정리 작업 |

가입자 수만으로 확장하지 않는다. 대기 시간과 실제 처리 시간을 분리해 본다.

## 비용 모델

`고정비(API·워커·DB) + 분석 분량·모델 호출 + 렌더링 시간 + 파일 저장·요청·전송`

월 예산·사용량·공급자는 미정이다. 특정 금액으로 운영 가능하다고 확정하지 않는다. 저장소 단가만으로 서비스 전체 비용을 계산하지 않는다.

## 구현할 비용 제한

입력 길이·용량, 사용자 동시 작업, 일별 분석 분량, 재시도 상한, 작업 시간, 파일 보관 기간, 예산 소진 후 신규 작업 접수 정책을 정한다. 분석 특징을 재사용하고 선택한 후보만 출력하는 설계도 비용 제한의 일부다.

## 공개 전 조건

소유권 검사·인증, TLS·비밀 주입, DB 백업·복구 연습, 비공개 파일 접근, 작업 복구, 사용량 관측을 검증한다. 현재 로컬 암호·무인증 Redis 설정을 공개망에 그대로 사용하지 않는다.
