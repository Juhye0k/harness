# 전사 품질 평가와 정답 입력 — TR-EVAL-002

음성 인식 정확도는 원음을 확인한 정답 전사와 비교해 평가한다. 정답이 없으면 길이·시간·누락 같은 구조 검사만 할 수 있으며, 그 결과를 인식 정확도로 표시하지 않는다.

> 상태: 평가 도구·같은 영상의 자동 점검 완료 / 정답 기반 품질 평가는 대기 · 기준일: 2026-11-16

[위키 홈](../README.md) · [개발 목차](README.md)

## 목적과 현재 결과

자동 검수의 표시를 실제 오인식으로 오해하지 않도록 평가한다. 전사 인식 문제와 자막 표시 문제를 분리하고, 사람이 원음을 확인한 정답만 정확도 계산에 사용한다. 새 AI 호출·DB 변경·전사 교정·SNS 게시는 없다.

승인된 같은 영상은 전사 121개·신뢰도 정보 121개·검토 대기 26개·인식 의심 신호 0개였다. 기존 전사와 새 전사의 121개 모두 문구와 시간이 같았다. 이 수치는 실행 결과의 일치이며 정확도가 아니다. 확인된 정답 전사는 0개이므로 글자 오류율(CER), 탐지 정밀도·재현율, 시간 절감 효과와 품질 합격 여부는 평가 불가다.

별도 일회성 진단으로 같은 모델의 구간 전사와 단어 목록을 비교해 한 글자 차이가 나는 구간 1개를 찾았다. 기존 신뢰도 규칙으로는 표시되지 않아 우선 청취할 사례로 비공개 보고서에 기록했다. 같은 모델의 보조 출력 차이는 정답이 아니며, 이 진단을 자동 검수 정책에 반영한 것은 아니다.

## 실행과 사람의 검수

실제 입력·음성·보고서는 Git에서 제외하는 비공개 폴더에 둔다. `report.json`은 완료 분석의 `GET /analyses/{id}/transcript-review` 응답이다. `audio.mp3`는 이미 저장된 검수용 음성이다. 이 명령은 API·모델에 접속하지 않는다.

```powershell
uv run python -m app.cli.evaluate_transcript `
  --report .artifacts/evaluation-input/report.json `
  --audio .artifacts/evaluation-input/audio.mp3 `
  --output .artifacts/evaluations/transcript-baseline
```

새 출력 폴더만 허용하며 기존 파일을 덮어쓰지 않는다. `review.html`은 원음 재생·인식 판정·정답 전사 입력·원음 확인 체크·JSON 다운로드를 제공한다. 자동 전사를 정답 입력란에 미리 채우지 않는다. 전체·검토 대상·인식 의심·비표시 표본 필터를 제공한다. 저장하지 않은 입력이 있을 때 페이지를 떠나면 경고한다. 다운로드한 정답 파일은 별도로 보관해야 하며 브라우저 저장소에 자동 수집하지 않는다.

표시된 구간과 표시되지 않은 구간을 함께 듣는다. 정답을 확정하기 어렵다면 `uncertain`으로 두고 정확도 판정에 포함하지 않는다. 일부만 검수한 결과를 전체 탐지율로 해석하지 않는다.

```powershell
uv run python -m app.cli.evaluate_transcript `
  --report .artifacts/evaluation-input/report.json `
  --references .artifacts/evaluation-input/references-reviewed.json `
  --output .artifacts/evaluations/transcript-reviewed
```

과거 전사와의 안정성 비교에는 `--comparison-transcript`를 추가한다. 비교 결과는 `run_agreement_not_accuracy`로 표시하며 정답 전사를 대신하지 않는다.

## 계산 계약과 하네스

- 평가 버전은 `transcript-evaluation-v1`이다. 분석 ID·전사 버전·검수 정책·구간별 원문과 시간을 SHA-256으로 묶는다. 다른 전사·오래된 파일·중복·없는 구간의 정답은 거부한다.
- 원음 확인 체크가 있는 인식 판정 `error/ok`만 탐지 평가에 사용한다. 원음 확인 체크가 있는 `reference_text`만 CER 계산에 사용한다. 판정만 입력한 것은 정답 전사가 아니다.
- CER은 Unicode NFC·casefold 후 영숫자 문자만 남기는 고정 정규화를 적용하고, 구간별 Levenshtein 편집 거리 합 / 정답 글자수 합으로 계산한다. 구간 경계를 넘어 오류를 상쇄하지 않는다. 표본 범위와 분모를 함께 반환한다. 빈 정답만 있거나 분모가 0이면 `null`이다.
- 인식 신호의 탐지 평가와 표시 문제를 포함한 검수 대기열 평가를 별도로 반환한다. 부분 검수에서는 검수한 표본의 정밀도·비표시 오류 비율만 계산한다. 전체 구간의 확정 인식 판정이 있어야 전체 재현율을 계산한다.
- `quality_pass`와 검수 시간은 합격 기준·실측값이 없으면 `null`이다. 명령의 성공 종료는 보고서 생성 성공이다.
- 정답은 최대 2,000개 구간·60,000자로 제한한다. 원본 전사·판정 DB·영상 파일을 수정하지 않는다. HTML은 사용자 문자열을 실행 가능한 코드로 넣지 않는다.

## 검증과 남은 작업

기본 `scripts/verify.py` 269개 통과, Ruff·서식·Alembic 오프라인 SQL 통과. Windows Chrome·실제 FFmpeg 합성 음성으로 재생 → 원음 확인·정답 입력 → JSON 다운로드 → CER·누락 오류 계산의 브라우저 통합 검사 1개가 통과했다. 해당 검사는 integration 표시로 일반 CI 통합 runner에서도 수집된다.

실제 비공개 평가 팩도 Chrome에서 전체 121개·검토 대상 26개·인식 신호 0개·비표시 표본 5개 필터와 저장 음성 재생을 확인했다. 이때 네트워크 외부 요청은 없었고 사람의 정답을 대신 입력하지 않았다.

Docker 복구 후 실제 PostgreSQL·Redis·Celery·FFmpeg·Linux Chromium 전체 통합 **60개가 통과**했다. 새 정답 입력 팩의 재생·판정·다운로드·CER 계산 검사도 포함한다. 기존 Starlette/httpx 사용 중단 예정 경고 1개는 남는다. 테스트 전용 컨테이너·네트워크·볼륨은 정리했다. 실제 AI·SNS 계정에는 접속하지 않았다.

최초 시도는 C 드라이브 공간 부족으로 중단됐다. 복구 후에는 기존 통합 이미지의 의존성을 재사용하고 이 워크트리의 `app/`, `tests/`, `scripts/`를 읽기 전용으로 연결해 새 이미지의 대용량 브라우저 설치를 피했다. 실행 전 호스트와 컨테이너의 상대 경로별 파일 내용 해시·파일 수·`uv.lock` 해시가 일치하는지 확인했다. 파일 정렬은 두 OS에서 동일한 상대 경로 문자열 기준으로 고정했다. 이는 최신 소스의 실제 인프라 통합 검증이며 새 production 이미지 빌드나 운영 배포 검증을 뜻하지 않는다.

위 269개·60개는 개별 워크트리 검증 이력이다. 이후 두 변경을 현재 작업 폴더에 통합하고 같은 영상의 표시 제약·원문 보존·무음 신호를 다시 측정했다. 원문·시각 범위는 통과했지만 표시 가독성 초안은 미달이다. [실제 품질과 통합 기록](harness/changes/transcript-quality-integration.md)을 따른다.

사람의 정답 전사에 근거한 인식 품질 판정은 남아 있다. 사용자는 확인한 정답 전사가 없다고 답했으며 코딩 에이전트가 이를 만들어 넣지 않는다. 시작 코드는 `fb9b793`과 요청 시 미커밋 수정이며 현재 변경도 미커밋이다. 푸시·Wiki 게시 전이다. 모델 사용량·비용의 제공값은 없으며 평가 명령 자체의 외부 호출은 0회다.
