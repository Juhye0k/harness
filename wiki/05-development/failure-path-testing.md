# 실패 경로 E2E 구현과 실행 — FAIL-E2E-001

통신 단절·분석 실패·워커 종료가 발생해도 작업이 중복 실행되거나 미검증 파일이 공개되지 않는지 확인한다. 먼저 실패별 예상 상태를 정하고, 일반 통합 검사와 실제 프로세스 종료 검사를 나눠 실행한다.

> 상태: 로컬 구현·기본 375개/통합 107개/강제 종료 3개 통과 · 기준일: 2026-11-18

[위키 홈](../README.md) · [개발 목차](README.md) · [기준 사용자 흐름](complete-flow.md)

## 검사하는 과정부터 이해하기

조회가 끊겼다고 영상 처리가 실패한 것은 아니다. 접수 응답이 유실돼도 서버에는 작업이 있을 수 있다. 반면 워커 프로세스가 종료되면 오류를 저장할 코드 자체가 실행되지 못할 수 있다.

**예상 상태 정하기 → 장애 위치 도달 확인 → 장애 발생 → DB·화면·파일·호출 수 비교 → 같은 작업 재조회** 순서로 확인한다. 도구의 정상 종료 여부뿐 아니라 결과 공개와 중복 실행 여부도 검사한다.

일반 통합 검사는 도구·제공자 경계의 오류와 브라우저 통신 단절을 재현한다. 별도 강제 종료 검사는 전용 환경에서 실제 프로세스를 종료하고 관리자 후속 처리를 확인한다.

## 구현한 구성과 실행

제품 보완은 `app/adapters/analysis_requests.py`, `analysis_request_receipts`와 migration `0008_analysis_requests`, 분석 API·웹 접수 복원, 자막 저장 미확정 내용 보존이다. 하네스는 `tests/integration/faults.py`의 작업별 장애/계수/준비 신호, `failure_artifacts.py`의 trace·화면, 실패 E2E 두 파일, `scripts/run_failure_drills.py`와 `drill_client.py`다. 제품 코드에서 tests를 import하지 않는다.

기본 검사와 일반 실패 E2E는 다음과 같이 실행한다. 신규 P0 13개는 기존 integration suite에 포함된다. 실제 외부 모델·YouTube·사용자 원본은 사용하지 않는다.

```powershell
uv sync --locked
uv run python scripts/verify.py
docker compose -f compose.integration.yaml build runner
docker compose -f compose.integration.yaml up --no-build -d api worker analysis-worker sns-worker
docker compose -f compose.integration.yaml run --rm runner
```

실제 컨테이너 종료는 위 suite가 종료한 뒤 별도로 실행한다. 오래된 로컬 이미지를 임의 재사용하지 말고 먼저 integration 이미지를 빌드한다. 이미지에는 `/uploads`의 appuser 권한과 source hash에 필요한 `AGENTS.md`, `compose.integration.yaml`이 필요하다.

```powershell
uv run python scripts/run_failure_drills.py
```

제어기는 이름을 직접 생성한 전용 프로젝트만 조작하고 끝에 해당 컨테이너·테스트 볼륨·네트워크를 정리한다. API 준비 조건은 고정 sleep이 아니라 healthy 상태이며 상한은 90초다. 작업 단계의 준비 신호에도 제한 시간이 있다. 코드·모델 실패와 테스트 환경 준비 시간 초과를 구분하며 제품 timeout을 늘리지 않는다. 새 수동 CI는 `.github/workflows/failure-drills.yml`이다.

강제 종료 결과는 `.artifacts/failure-drills/<실행ID>/result.json`, 원시 진단 로그는 같은 로컬 폴더의 `private-logs.txt`다. CI에는 정제한 result JSON만 7일 보관한다. 임시 데모 세션은 격리 Redis 안에만 두고 결과·공개 로그에 넣지 않는다. 일반 실패 E2E의 trace·화면·요청 목록은 `/data/e2e/failures/<실행ID>/`이며 기존 CI 합성 증거 수집에 포함된다. 종료 전 증거를 수집하고 실제 사용자 trace를 공개하지 않는다.

## 목표와 범위

정상 흐름의 기능을 늘리기보다 실패 상황에서 DB의 업무 상태·화면 안내·파일·외부 호출 수가 서로 맞는지 확인한다. 한 번에 한 장애를 주입해 원인을 특정하고, 수정한 제품 동작을 회귀 검사에 연결한다. 실제 키·사용자 원본·SNS 계정은 사용하지 않는다.

첫 범위는 분석 실패·조회 통신 단절·접수 응답 유실·렌더링 실패·중복 전달·SNS 결과 미확정·워커 강제 종료다. 자동 재시도·유료 대체·감시 서비스·lease/outbox 도입은 포함하지 않는다. 테스트 설정을 일반 API의 숨은 장애 옵션으로 노출하지 않는다.

## 상태 판정 원칙

1. GET 통신 실패는 업무 실패가 아니다. DB 상태를 바꾸지 않고 같은 ID로 다시 조회한다.
2. POST 응답 유실은 접수 여부 미확정이다. 접수 완료 여부를 확인하기 전에 새 작업을 만들지 않는다.
3. 처리 오류를 워커가 잡아 DB에 저장했다면 failed다. 검사하지 않은 출력 파일·SRT·SNS 이동은 허용하지 않는다.
4. 프로세스 전체 종료는 예외 처리 코드도 실행하지 못한다. 현재 계약에서는 pending/running이 남을 수 있으며, 자동으로 failed가 됐다고 기대하지 않는다.
5. SNS 전송 결과를 알 수 없으면 unknown을 유지한다. 강제 종료로 running이 남은 SNS 작업은 실행 중단을 확인한 관리자가 기존 CLI로 unknown으로 전환한다. 원격 접수 가능성이 있으므로 일반 영상 작업처럼 failed로 확정하지 않는다.
6. 운영자 확정 뒤 늦게 도착한 완료는 조건부 갱신으로 거절한다. 새 시도를 시작하는 것은 기존 작업 조회와 구분한다.

## 응답 유실을 복원하는 방식

### 같은 분석 요청의 중복 생성 방지

멱등성은 같은 요청을 다시 보내도 새 작업을 만들지 않는 성질이다. 신규 웹 분석 요청에 UUID request_id를 부여하고 전송 전에 브라우저에 보관한다. 서버는 신뢰할 수 있는 로그인 사용자 범위와 request_id를 함께 고유 키로 사용한다. 인증 없는 localhost 개발 모드는 서버가 정한 개발용 범위를 사용하며 요청 본문의 소유자 값을 신뢰하지 않는다.

요청 receipt에는 정규화한 입력의 해시·분석 ID·생성 시각을 저장한다. PostgreSQL 복합 기본키 `(owner_key, request_id)`와 `INSERT ON CONFLICT`로 동시 등록을 직렬화한다. 동일 키·동일 입력은 같은 분석, 동일 키·다른 입력은 409로 거절한다. 기존 성공·실패·미확정 상태를 그대로 반환하며 자동으로 새 분석을 만들지 않는다. 접수 영수증과 업무 행을 같은 DB 트랜잭션에 저장하되 Redis 발행까지 원자적이라고 주장하지 않는다. pending 상태의 재접수도 새 메시지를 발행하지 않는다.

응답 유실 시 웹은 원래 키로 상태를 GET 조회한다. receipt가 없다는 응답도 진행 중인 등록과 경쟁할 수 있으므로 즉시 새 POST를 자동 실행하지 않는다. 새로고침도 재접수가 아니라 저장한 키의 조회로 복원한다. 동일 키 재접수 기능을 제공한다면 사용자 동작으로 제한하고 같은 키를 유지한다.

접수 조회 보장 기간은 생성부터 7일이다. 만료·자료 삭제는 410으로 거절하고 부모 분석이 삭제되면 receipt 참조를 NULL로 남겨 묵시적인 새 분석 생성을 막는다. 민감 내용 없는 표식은 만료 후 30일까지만 보관한다. 자료 삭제 시 만료 시각도 앞당긴다. 그 이후의 키 재사용은 보장 범위 밖이며 웹은 오래된 요청을 자동 재접수하지 않는다. 원본 URL·전사·토큰을 receipt 로그에 중복 저장하지 않는다.

자막 저장은 요청 body를 응답 확인까지 브라우저에 보관한다. 새로고침 시 최신 저장본의 원본 버전·확인 상태·문구·시간이 pending body와 일치하면 그 버전을 복원한다. 더 최근의 다른 저장본 때문에 일치하지 않으면 미확정 편집 내용을 유지하고 사람이 같은 내용을 저장하도록 한다. 서버의 불변 내용 해시가 같은 편집 버전을 재사용한다. 응답 유실을 성공으로 가정하거나 다른 편집본으로 대체하지 않는다.

대상: `api/analyses.py`, `adapters/analysis_repository.py`, `models.py`, 최신 Alembic head 다음 migration, `static/recommendations.js`. 별도 receipt 조회 경로도 소유권·만료 검사를 거쳐야 한다.

### 화면과 관리자 안내

오류 안내는 처리 실패·조회 실패·접수 미확정·SNS 결과 미확정을 구분한다. 조회 버튼은 GET만 수행한다. 결과가 검증되지 않으면 완성본 링크를 숨기고, 이전 편집본의 출력과 새 편집을 섞지 않는다. 무한 폴링·자동 재전송·같은 실패의 무한 새 작업 생성은 추가하지 않는다.

워커 종료를 감지하는 기능은 이번에 만들지 않는다. UI와 테스트가 DB의 마지막 기록을 현재 프로세스 생존의 증거로 표현하지 않도록 검토한다. 필요한 수동 확정은 기존 명령을 재사용한다.

- 영상·분석: `python -m app.cli.fail_job JOB_UUID --confirmed-stopped --reason "중단 확인 사유"` (`--analysis`로 분석 선택).
- SNS: `python -m app.cli.mark_upload_unknown UPLOAD_UUID --worker-stopped`.

두 명령의 확인 플래그 자체가 프로세스 종료를 증명하지 않는다. 테스트 제어기가 컨테이너 종료를 먼저 확인해야 한다. queued 잔류를 pending/running 전용 실패 확정 명령에 억지로 포함하지 않는다.

## 하네스 구성과 실행 순서

### A. 일반 CI: 결정적으로 재현하는 실패

`tests/integration/fixture_analysis_worker.py`, `fixture_worker.py`, `fixture_sns_provider.py`를 확장했다. 장애 지점·호출 계수는 격리 Redis의 작업 ID 범위로 관리하고 실행이 끝나면 해당 테스트 프로젝트의 볼륨과 함께 정리한다. 사용자 제목·URL을 새로운 범용 장애 명령으로 해석하지 않는다.

대역은 실패를 주입할 도구 경계만 바꾸고 실제 DB·Redis·Celery를 사용한다. `FaultProviders(job_id)` 같은 테스트 전용 래퍼와 기존 providers 주입 지점을 이용한다. 프로덕션 코드에 임의 실패용 API를 추가하지 않는다. 브라우저 조회 중단과 응답 유실은 Playwright의 네트워크 제어로 재현한다.

새 검사는 `test_failure_paths.py`에 P0 흐름을, `test_analysis_request_recovery.py`에 receipt 경쟁·소유권·만료·응답 유실을 둔다. 기존 성공 E2E와 이미 있는 실패 검사는 유지한다. 모든 시나리오를 처음부터 긴 영상으로 반복하지 않고 공통 준비는 재사용하되 작업별 장애 상태와 계수는 분리한다.

각 검사는 **정상 준비 → 장애 위치 도달 확인 → 장애 주입 → DB·화면·파일·호출 수 검사 → 장애 해제/관리자 처리 → 같은 ID로 재조회** 순서다. 임의 sleep으로 성공을 기대하지 않고 준비 신호와 제한 시간 내 조건을 기다린다. 처음에는 P0만 기존 integration CI에 포함한다.

### B. 격리 장애 실험: 실제 프로세스 종료

`scripts/run_failure_drills.py`는 호스트에서 실행하는 제어기다. 이 파일은 제품 워커가 아니라 테스트 자원 수명주기를 담당하는 하네스다. Docker CLI는 인자 배열로 호출한다. 생성한 `shortform-failure-<실행ID>` 형식·볼륨 소유 범위·읽기 전용 코드 마운트·호스트 포트 없음·test 환경·실제 키 없음·가짜 YouTube client를 확인한다. 개발/운영 컨테이너·DB·영상 볼륨은 공유하지 않고 runner에 Docker 소켓을 마운트하지 않는다.

워커가 queued를 실제로 running으로 선점한 후 테스트 준비 신호를 보낸다. 신호 확인 뒤 해당 워커 컨테이너를 강제 종료한다. 첫 실험의 기준은 선점 후 처리 전이며, FFmpeg가 실제 실행 중이었다고 과장하지 않는다. FFmpeg 실행 중 종료를 추가한다면 PID/시작 신호까지 별도로 증명한다.

API/실행 주체의 종료 확인 → 기존 관리자 명령 → API 재기동·조회 → 늦은 완료 거절과 무재실행 순서를 검사한다. 분석·SNS는 실행 경계와 상태 계약이 다르므로 영상 실험을 통과한 것으로 대신하지 않는다. 종료·정리는 finally에서 수행하되 종료 실패를 숨기지 않는다.

이 실험은 일반 suite와 분리한 수동 실행 CI(`workflow_dispatch`)부터 시작한다. 재현성과 소요 시간을 확인한 뒤 PR 필수 검사 포함 여부를 정한다. 한 작업의 장애 실험으로 다른 병렬 테스트를 중단시키지 않는다.

## 증거와 완료 기준

시나리오별로 코드/설정 버전, 작업·편집·업로드 ID, 장애 지점 도달·주입·확인 시각, 상태 전이, 실행/호출/전송 계수, 원본·출력 해시, 화면·trace·정제 로그를 남긴다. 기존 FLOW-001 CI artifact 방식을 재사용하고 원시 전사·비밀값은 게시하지 않는다.

합격은 오류 메시지 표시만으로 판단하지 않는다. 예상한 DB 상태·HTTP 접근·화면·실행 수가 모두 일치해야 한다. 같은 실행에서는 도구 처리 최대 1회, 자동 AI 재호출 0회, 미승인 SNS 전송 0회, 원본 변경 0건이다. 별도로 사용자가 명시적으로 시작한 새 작업을 같은 실행으로 세지 않는다.

구현은 **기준 스냅샷 확정 → P0 장애 대역·관찰 추가 → 분석 receipt 및 발견한 제품 결함 수정 → P0 전체 E2E → 실제 워커 종료 실험 → CI/문서 반영** 순서로 진행한다. 각 수정 후 해당 실패 검사와 정상 흐름을 재검사하고 최종 기본·실제 인프라 integration을 실행한다. 동시성의 재현성은 해당 검사에 한해 반복하며 전체 suite를 근거 없이 반복하지 않는다.

실행 결과·초기 실패·한계는 [작업 기록](harness/records/2026-11-17-failure-path-plan.md)에 남긴다. 자동 장애 감지·자동 재실행·실제 제공자 장애 재현은 구현 범위 밖이다.
