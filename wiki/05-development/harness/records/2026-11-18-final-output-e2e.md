# 원음 확인부터 최종 다운로드까지 — FLOW-E2E-003

> 실제 영상에서 원본 자막과 편집 자막이 겹치던 두 구간을 지정해 다시 출력했다. MP4에서는 해당 구간의 편집 자막만 숨겨졌고, 다운로드용 SRT에는 검수한 자막 34개의 문구와 시간이 모두 남았다.

## 2026-11-20 원본 자막이 있는 구간의 재출력

후속 요청은 같은 검수본으로 자막 중복을 해소하고 실제 재생 화면과 다운로드 파일을 확인하는 것이었다. 완료 기준은 지정 구간에서만 편집 자막이 사라지고, 같은 작업의 SRT에는 검수한 자막이 모두 남는 것이다.

11월 19일 출력에서 자막이 겹쳤던 클립을 main `b09265e`로 다시 출력했다. 사용자가 원음과 시간을 확인한 편집 버전과 원본을 격리 환경에 복원하고, 기존 원본 화면 관측 18개의 프레임 해시를 대조해 연속된 두 구간을 지정했다. 구간 시각은 클립 시작 기준이다.

| 클립 구간 | 실제 출력에서 확인한 결과 |
|---|---|
| 0.140~12.940초, 17.240~32.240초 | 0.540초와 31.790초 표본에서 원본 화면 자막이 보였고 그 아래의 편집 자막은 사라졌다. |
| 12.940~17.240초 | 15.940초 표본에서 편집 자막이 다시 보였다. |

이전·새 MP4의 969프레임을 같은 표시 시각에 맞춰 아래 자막 띠를 비교했다. 지정 구간 안에서만 편집 자막을 숨기는 규칙과 어긋난 프레임은 0개였다. 같은 출력 작업에서 받은 SRT의 번호·문구·줄바꿈·클립 기준 시각을 검수본과 34개 모두 대조했고, SRT 파일도 이전 출력과 바이트 단위로 같았다.

세로 MP4는 720×1280, 32.3323초였다. 영상과 음성을 끝까지 디코딩했고 Chrome에서 1배속 재생이 끝까지 진행됐다. 브라우저에서 받은 MP4와 SRT는 각각 API에서 직접 받은 파일과 일치했다. 브라우저 재생 통계에는 표시 누락 4프레임이 기록됐다.

검증 범위는 실제 클립 한 건이다. 원본 자막 경계는 100ms 간격으로 화면을 관측해 정했으며 약 ±200ms의 불확실성이 있다. 기본 검사 425개가 통과했다. 이 출력의 SNS 게시는 별도 단계다.

### 같은 클립으로 재검사하는 방법

Windows에서 승인된 원본·편집 버전과 구간 지정 전후의 MP4, 같은 작업에서 받은 SRT를 준비한다. 다음 명령의 파일명은 로컬 복사본을 가리킨다.

```powershell
ffprobe -v error -select_streams v:0 -show_entries frame=best_effort_timestamp_time -of csv=p=0 after.mp4
ffmpeg -v error -xerror -i after.mp4 -map 0:v:0 -map 0:a:0 -f null -
uv run python scripts/verify.py
```

1. 두 MP4에서 프레임 표시 시각 목록이 같은지 확인한다. 각 파일에 FFmpeg 필터 `crop=720:120:0:754,format=gray`를 적용해 자막 띠를 잘라낸다. 각 프레임에서 밝기 180을 넘는 픽셀이 100개를 초과하면 편집 자막이 보이는 것으로 센다. 이 좌표와 기준은 이 클립의 출력 프로필에 맞춘 값이다.
2. 지정 구간 안의 새 자막 띠는 비어 있어야 한다. 그 밖에서는 이전 출력과 표시 여부가 같아야 한다. 경계에서도 같은 규칙을 적용하고, 두 구간 안쪽과 사이에서 원본 화면과 띠를 직접 비교한다.
3. UTF-8 SRT 블록을 번호순으로 읽어 검수본의 줄별 문구와 비교한다. 각 자막의 시작·종료 시각에서 클립 시작 시각을 뺀 값이 SRT 시각과 밀리초 단위로 일치하는지 확인한다.

## 2026-11-19 실제 출력 검증

P3 요약. 사용자가 실제 편집기에서 원음을 확인하고 검수본을 저장했다. 검수 완료 상태의 새 불변 버전에서 기존 34개 자막의 문구·시간·전사 구간이 모두 유지됐다. 이미 완료된 출력 작업을 조회해 두 파일을 내려받았다. 검증 과정에서 출력 작업을 다시 접수한 횟수는 0회다.

| 검사 | 관측 결과 |
|---|---|
| MP4 | `portrait-edited-v2`, 720×1280, 정사각형 픽셀, 32.3323초. 목표 32.320초의 ±0.100초 범위 안이며 영상·음성 각 1개 트랙을 끝까지 디코딩했다. |
| SRT | UTF-8 자막 34개의 문구·줄바꿈·클립 기준 시간이 검수본과 일치했다. 모든 자막이 한 줄이며 표시 시간은 0.50~1.70초, 시간 겹침은 0건이다. |
| 다운로드·원본 보존 | 브라우저와 직접 API에서 받은 MP4·SRT 바이트가 각각 일치했다. 원본 영상의 SHA-256도 이전과 일치했다. |
| 화면 | 원본 화면 전체와 아래 자막 띠가 보였다. 자막 34개 구간의 중앙 프레임에서 새 자막을 확인했다. 표본 일부에서 원본에 포함된 자막과 새 자막이 동시에 보였다. |

검수 버전과 작업 ID, 두 파일 해시 및 화면의 제한을 SNS 검증 담당에 전달했다. 이번 검증은 실제 영상 한 건의 파일과 화면을 대상으로 했다. YouTube 게시에는 해당 파일·계정·설정에 대한 별도 승인이 필요하다.

## 사람의 판단과 남은 작업

### 2026-11-19 패널 재개

- P2 요약. PR #15 병합 후 기존 전용 트리에서 실제 검증을 재개한다. 1번이 검증된 main과 `0009_caption_render_jobs`를 적용한 뒤에만 조건부 저장으로 고정 초안을 미확인 상태로 등록한다. 출력은 해당 초안의 사용자 원음 확인을 전제로 한다.
- main `45739f449a5c46a0f24a80aea6b8ccd81809d713`의 CI는 기본 421개와 통합 110개를 통과했다. 이전 Wiki 게시는 `6853cfb7`이다. 격리 환경에서 통과한 v2 전체 흐름 세 파일의 4개 통합 검사에 사용한 앱·마이그레이션·통합 테스트는 이 main과 동일하다.
- Windows에서 고정 파일·원본 SHA-256, 34개 자막의 82어절과 동일한 18구간의 전체·구간별 7/208을 다시 대조했다. Chrome에서 같은 34개의 문구와 시간을 읽고 원본의 58.70초, 59.36초, 90.80초 재생을 확인했다. 시작 58.70–59.60초와 끝 91.60–92.00초의 잘린 단어는 사용자 확인 대상이다.
- 기존 개발 코드의 읽기 전용 API 검사에서 분석 성공, 후보 범위, 전사 구간 일치, 원본 전체 SHA-256과 범위 응답 206, 기존 29개 버전 조회를 확인했다. 전환 전 전사와 편집 버전의 해시를 비공개 인수 JSON에 기록했다.
- 전환 중 읽기 검증에서 v2 출력 프로필과 동일한 원본·전사 해시, 기존 버전 조회를 확인했다. 실제 저장은 1번의 실행 소스·스키마 검증 인수를 기다린다.
- 4번 트리에서 Ruff, 기본 405개, Alembic 오프라인 SQL을 재검사했다. 처음에는 기존 pytest 임시 폴더 접근 권한 때문에 실패했고, 작업 트리의 새 임시 경로를 지정해 통과했다. 통합 107개는 기본 검사 범위에서 제외했다.

사용자가 지정한 전용 트리에서 자동 검사와 읽기 검증을 수행했다. 당시 원음 확인을 기다렸다. 초안의 끝은 다음 단어 시작을 사용하는 표시 시각이며, 자동 검사에서는 잘린 두 경계의 실제 발화 끝을 확인할 수 없었다.

제품 외부 AI 호출·실계정 게시 없음. 제품 코드는 PR #15로 통합됐고 후속 검증 기록의 main·Wiki 반영은 [재개 기록](2026-11-19-flow-resume.md)과 완료 보고에서 확인한다.

### 같은 날 실제 검증 재개

역할 4 전용 트리에서 고정 초안과 원본 해시, 34개 자막의 82어절, 전체·구간별 7/208을 다시 확인했다. Chrome에서 34개 문구·시간을 대조하고 58.70초, 59.36초, 90.80초의 원본 재생을 확인했다. 사용자는 아직 원음을 검토하지 않았다고 답했다. 기본 검사 405개, Ruff와 Alembic 오프라인 SQL이 통과했다. 기본 검사에서 통합 107개는 제외됐다. 최초 접속 시 개발 API가 연결을 거절해 역할 1의 실행 환경 확인을 기다렸다.

역할 1이 main `45739f4`와 스키마 `0009_caption_render_jobs`를 확인한 뒤, 실제 편집기에서 기존 29개 버전을 조건으로 34개 초안을 한 번 저장했다. 이전 버전은 그대로 조회됐고, 새 버전의 구간 ID·문구·줄바꿈·시간·미검수 상태가 새로고침 후에도 고정 초안과 일치했다. 원본 재생과 첫 자막 표시도 확인했다. 출력 버튼은 비활성이었고 직접 출력 요청은 HTTP 409와 `SUBTITLE_REVIEW_REQUIRED`를 반환했다. 출력 작업 ID는 비어 있었다. 별도 HTTP 조회로 원본·전사·후보 구간 해시와 새 버전을 다시 확인했다.

이 단계는 미검수 버전의 보호 규칙을 확인하는 데서 마쳤다. 이후 사용자가 확인한 최종 버전의 다운로드와 파일 인수 결과는 이 문서 상단에 기록했다.

## 포트폴리오 요약

미검수 저장, 사용자 확인, 확정 버전의 출력과 다운로드를 실제 영상 한 건에서 연결했다. 바이트 검증과 화면 검사를 함께 수행해 원본 자막과 새 자막이 동시에 보이는 구간을 확인했다.
