# 원본 화면을 보존하는 세로 출력 — FLOW-LAYOUT-003

> 원본 화면 전체를 보존하는 세로 출력에 전용 자막 띠를 추가했다. 원본 자막이 보이는 것으로 확인된 구간만 새 자막을 숨겼다. 합성 영상과 격리 PostgreSQL에서 검증했으며 실제 새 편집본은 원음 확인을 기다린다.

## 요청과 완료 기준

사용자 요청 요약. 3번 전용 작업 트리에서 원본 화면과 음성을 보존하며 세로 출력의 여백과 중복을 개선한다. 확인된 원본 자막 구간만 사용하고, 확인되지 않은 구간에서는 편집 자막을 계속 표시한다. 기존 출력 재사용과 다운로드·SNS 연결을 검증한다.

시작 커밋은 `12673d88f8b1fa5a5cc5cd808781d3afd305e0d4`다. 전용 작업 트리는 깨끗했고 원래 루트에 별도 미커밋 작업이 있었다. 실제 새 초안의 원음 확인, 유료 모델 호출, SNS 게시는 이번 검증에서 제외한다.

## 출력의 표시 규칙

기존 세로 MP4의 2·8·27초 프레임 모두에서 화면에 새겨진 자막과 편집 자막이 함께 보였다. 720×1280 화면에서 원본의 높이는 404픽셀이었다. 원본을 확대해 화면을 채우면 기사 본문이나 화자가 잘릴 수 있어, 새 프로필은 원본 전체를 화면 비율대로 맞추고 어두운 청회색으로 남은 영역을 채운다. 높이 192픽셀의 자막 띠를 원본 바로 아래에 붙여 원본과 자막 띠를 함께 가운데 놓는다. 가로 원본이 차지하는 높이는 화면 비율에 제약받는다.

기존 내보내기 API의 빈 본문은 `portrait-edited-v2`로 저장된 편집 자막을 모두 표시한다. 선택 입력 `source_captions`에는 원본의 `source_sha256`과 자막이 실제로 보이는 `visible_spans`를 담을 수 있다. 원본과 연결한 해시는 제출 시 검증하며, 각 구간의 `start_ms`와 `end_ms`는 원본 기준 밀리초로 입력한다. 구간은 후보 안에서 시간순이며 서로 겹치지 않아야 한다. 서로 붙어 있는 구간은 하나로 합친다.

원본 자막이 보인다고 확인한 구간과 편집 자막이 겹치는 부분만 MP4의 새 자막에서 제외한다. 확인 범위가 비어 있거나 부분 관측이라면 나머지 구간의 편집 자막은 그대로 표시한다. ASS 렌더러의 10ms 단위에서는 확인 범위 안쪽으로 반올림해 확인되지 않은 시간을 숨기지 않는다. 원본 화면에 새겨진 글자와 편집 버전 전체를 담은 SRT는 보존된다. 임의의 영상에서 원본 자막의 존재를 자동 판정하는 기능은 없으므로 관측 없는 구간에서 중복이 남을 수 있다.

## 버전과 출력 파일의 연결

Alembic `0009_caption_render_jobs`는 출력별 설정을 별도 테이블에 고정한다. 같은 편집 버전·프로필·원본 해시·정규화한 관측 구간의 요청은 같은 작업 ID를 사용한다. 프로필이나 관측 범위가 바뀌면 별도 작업이 생성된다. 기존 v1 작업의 ID·MP4·SRT는 유지된다. SNS가 선택한 작업 ID와 파일 해시를 확인하는 로직은 기존 계약을 사용한다.

편집기 GET은 현재 `export_profile`을 제공하고, 편집 버전은 연결된 `render_job_id`와 `render_profile`을 제공한다. 현재 프로필의 작업이 여럿이면 가장 최근 생성 작업을 보여준다. v1 작업만 있으면 이전 ID와 프로필을 제공하므로 웹은 기존 결과를 표시하면서 새 프로필의 출력을 허용할 수 있다. 이전 워커가 새 작업을 일반 추출로 처리하는 일이 없도록 v2 작업의 매핑이 남은 상태에서는 마이그레이션 내리기를 거부한다.

## 검증과 인수

- `uv run python scripts/verify.py`에서 Ruff 검사·서식, 기본 414개, Alembic 오프라인 SQL을 모두 통과했다. 기존 Starlette/httpx 경고 1개가 남았다.
- 관련 단위·FFmpeg 검사 37개를 통과했다. 합성 영상으로 720×1280, 3초 ±0.1초, 음성, 전체 디코딩, 원본 해시, 배경 픽셀, 원본 좌우 내용과 우측 삽입 화면, 두 줄 한글 자막의 안전 영역을 검사했다. 확인 구간과 미확인 구간에서 각각 원본 자막과 편집 자막이 보이는지 프레임을 확인했다.
- 생성한 격리 PostgreSQL에 `0008_analysis_requests`부터 `0009_caption_render_jobs`까지 실제 적용했다. 렌더 입력·레거시 다운로드 회귀와 기존 소유권·삭제 검사 2개가 통과했다. 워커 대역이 필요한 동시 처리 검사 1개는 이 실행에서 건너뛰었다. 결합된 Redis·Celery·브라우저 검사와 Wiki는 통합 담당이 확인한다.
- 사용자는 원본 보존, 직접 원음 확인, 실제 SNS 게시 제외를 정했다. 에이전트는 프로필·선택 입력·저장 구조를 구현하고 기존 프레임과 합성 영상으로 검증했다. 개발 에이전트 사용량과 비용은 도구에서 확인되지 않았다.

## 11월 19일 렌더 검사 수정

사용자는 PR [#15](https://github.com/Juhye0k/short-form/pull/15)의 Linux 실패를 재현하고, 글자 크기·중앙 정렬·클리핑을 검증한 수정 커밋을 통합 담당에게 넘기도록 요청했다. 작업 시작점은 역할 3의 `178f2937a3ec0336d5efcef5f89ccc2f6c386363`이다. 실패한 PR head `b968ff5d3f023be2e82439c45c832dc68d065313`와 이 시작점의 렌더러·ASS 스타일·검사 파일은 동일하다.

GitHub Actions의 기존 `checks`는 밝은 글자 픽셀의 시작점이 160보다 작아야 한다는 검사에서 실제 값 174로 실패했다. `integration`은 통과했다. Windows에서 맑은 고딕으로 같은 14자 두 줄을 그리면 폭이 각각 436·437픽셀, 높이가 29픽셀이었다. 줄별 중앙은 x=360.5와 360.0이었다.

Ubuntu 26.04 WSL의 FFmpeg 8.0.1과 Noto Sans CJK KR에서 기존 검사가 동일한 값 174로 실패했다. 두 줄의 폭은 371·372픽셀, 높이는 26픽셀, 중앙은 각각 x=360.0과 359.5였다. 같은 Linux FFmpeg와 원본에서 폰트만 맑은 고딕으로 바꾸면 Windows의 폭·높이·중앙 좌표가 재현됐다. 기존 검사의 고정 좌표는 맑은 고딕의 글자 폭을 가정하고 있었다.

원본 자막의 표시·억제·복원 시점 검사를 유지하고, 자막의 기하 조건은 별도 검사로 확인한다. 각 줄의 좌우 48픽셀 여백, x=359.5 기준 5픽셀 이내의 중앙 정렬, 줄 사이 공백, 세로 여유 및 실제 칠해진 높이를 검사한다. 동일 폰트·배율로 두 배 큰 화면에 직접 그린 기준과 줄별 밝은 픽셀을 비교한다. 교집합이 합집합의 97% 이상이어야 하므로 H.264의 경계 변화에는 여유를 주면서 줄 끝이 잘리는 회귀를 검출한다.

- 수정한 FFmpeg 렌더 검사 8개가 Windows, Ubuntu WSL, Debian 12 격리 컨테이너(FFmpeg 5.1.9)에서 각각 통과했다. Debian에서도 기존 검사는 동일한 값 174로 실패했다. 기준과 프레임의 줄별 글자 픽셀 일치율은 세 환경에서 98.4% 이상이었다. 두 Linux 환경에서 자막을 가로로 24픽셀 이동하거나 양쪽 글자 끝을 각각 약 50픽셀 지우면 새 검사가 실패했다.
- Windows에서 pytest 임시 경로를 전용 트리 안에 두고 `uv run python scripts/verify.py`를 실행했다. Ruff, 기본 검사 415개, Alembic 오프라인 SQL을 통과했다. 통합 검사 108개는 기본 검사에서 제외됐다. 렌더러와 프로필은 시작 커밋의 코드를 사용했다. 결합 PR의 새 head와 Wiki 게시 검증은 통합 담당이 맡는다.

## 포트폴리오에 옮길 근거

세로 화면을 채우는 과정에서 가로 영상의 기사와 화자가 잘릴 수 있었다. 화면을 보존하고 자막 띠를 따로 배치한 후, 원본 자막이 보이는 것으로 확인된 구간에만 편집 자막을 숨겼다. 같은 편집 버전의 여러 출력 조건을 작업 ID로 고정해 기존 다운로드를 유지하고 각 출력의 증거를 독립적으로 확인할 수 있게 했다.
