# 쇼츠 제작 화면과 사용자 흐름 — FLOW-WEB-002

> 링크나 파일을 넣어 쇼츠를 만들고, 프로젝트에서 후보를 다시 열어 편집·다운로드·YouTube 게시까지 이어갈 수 있다. 후보, 편집 버전, 출력 작업을 이동 중에도 유지하도록 화면을 연결했다.

[위키 홈](../../../README.md) · [작업 기록 목차](README.md) · [사용 흐름](../../complete-flow.md)

사용자 요청 요약은 초기 참고 서비스와 비교해 Shortform 페이지와 사용 흐름을 완성하는 것이다. 시작 커밋은 `edff0cc`이고 추적 작업 폴더는 깨끗했다.

완료 기준은 홈에서 입력을 시작하고 서버의 프로젝트 목록에서 작업을 다시 찾아 후보를 재생할 수 있는 것이다. 저장한 출력의 다운로드와 YouTube 화면에서 해당 후보로 돌아갈 수 있어야 한다. 기존 주소, 원음 확인·게시 승인, 중복 접수 방지와 로그인 범위를 유지한다.

## 구현과 확인

Alphacut의 공식 안내에서 프로젝트를 열어 후보를 재생하고 편집·다운로드·게시로 이동하는 순서를 참고했다. [쇼츠 생성과 결과 확인](https://alphacut.video/blog/create-first-short) · [다운로드와 SNS 업로드](https://alphacut.video/blog/upload-shorts)

| 사용 단계 | Shortform에서 연결한 동작 |
|---|---|
| 시작 | 홈에서 링크나 로컬 파일을 선택하고 분석을 시작한다. 구간을 직접 지정하는 10초 추출은 전용 화면에서도 사용할 수 있다. |
| 프로젝트 재개 | 서버에서 분석 상태와 생성 시각, 후보 수를 조회한다. 로그인 상태에서는 본인의 만료되지 않은 프로젝트만 목록에 표시한다. |
| 후보 비교와 편집 | 점수와 근거를 보고 원본에서 해당 구간을 재생한다. 선택한 후보는 주소에 기록해 새로고침이나 편집 후 돌아올 때 복원한다. |
| 다운로드와 게시 | 검수본에 연결된 출력이 성공한 경우 MP4와 SRT를 열 수 있다. 게시 화면은 선택한 파일과 제목을 불러오고, 채널 연결을 마치고 돌아왔을 때도 같은 편집 버전을 가리킨다. |

첫 브라우저 실행에서는 두 검사가 실패했다. 하나는 게시 주소에 업로드 ID만 있을 것으로 가정했고, 다른 하나는 화면에 영상 요소가 하나일 것으로 가정했다. 게시 주소에서 동일한 분석·후보·검수 버전·출력 작업 ID가 보존되는지 검사하고, 최종 게시 확인 영상의 재생 속성을 직접 확인하도록 갱신했다.

격리된 PostgreSQL·Redis·Celery와 Chromium에서 관련 통합 테스트 41개를 통과했다. 프로젝트를 다시 여는 동작, 후보 재생과 선택 복원, 자막 저장·출력 차단, MP4·SRT 바이트와 게시 대역이 받은 영상의 일치, 계정별 프로젝트 조회 범위를 확인했다. 실제 외부 AI 호출과 YouTube 재게시는 이번 검증 범위에 포함하지 않았다. 데스크톱·모바일에서 제작 홈과 편집 화면을 확인했다.

저장소 표준 검사는 Ruff, 기본 검사 422개, Alembic 오프라인 SQL까지 통과했다. Wiki 원본 빌드에서 101개 페이지와 내부 링크 738개를 확인했다.

사용자는 초기 참고 서비스와 비교해 사용자 흐름을 완성해 달라고 요청했다. 홈을 제작 화면으로 바꾸고 10초 추출을 별도 메뉴에 두는 구성은 이번 구현에서 정했다. 작업·검사에 사용한 도구는 Windows PowerShell, Docker, uv와 Playwright다. 개발 에이전트 사용량과 비용 자료는 없으며, 변경과 이 기록은 로컬 작업 트리에 있다.

## P2. 실제 링크로 시작할 때 다운로드 오류

사용자는 제작실에서 `DOWNLOAD_FAILED`를 보고했다. 먼저 연 8016 포트는 통합 검사 환경이다. 이 환경의 분석 워커는 합성 샘플 링크만 읽으며 최근 두 작업은 다운로드 단계에서 실패했다. 완료 기준은 실제 다운로드 워커에 연결한 최신 제작 화면을 열고 공개 샘플로 영상 다운로드를 확인하는 것이다.

실제 앱과 다운로더를 8000 포트에서 실행했다. 새 Compose 프로젝트에 별도 볼륨을 사용했고, 공유 볼륨의 첫 동시 초기화가 실패해 서비스 생성 순서를 지정해 다시 시작했다. 공개 MP4를 받아 10.0초 영상으로 추출했다. 결과 파일 다운로드는 HTTP 200이었고 영상·음성 트랙과 원본 보존 검사를 통과했다.

사용자가 시도한 YouTube 링크는 실제 워커에서도 실패했다. 원본 주소와 로그 원문을 작업 기록에 남기지 않고 오류 유형만 확인했으며 로그인 확인과 요청 제한 응답이 감지됐다. 이제 오류 화면의 **영상 파일로 다시 시작**을 누르면 파일 선택 버튼이 있는 입력 영역이 펼쳐진다. 복구 화면 이동은 분석을 접수하지 않는다. Chromium에서 실패 경로 5개와 파일 업로드·추천 대역 흐름 1개를 통과했다. Ruff, 기본 검사 422개, Alembic 오프라인 SQL도 통과했다.

8000 포트에는 로컬 환경에 설정된 Groq 무료 전사·추천을 사용하도록 연결했다. 이번 문제 확인 과정에서 Groq 전사·추천 호출과 YouTube 게시를 실행하지 않았다. YouTube 링크 다운로드에는 원격 접근 제한이 남아 있으므로 보유한 원본 파일로 입력할 수 있다. 작업 기록은 로컬에 작성했다.

## P3. Groq 후보 채점의 접근 거부

사용자는 `PROVIDER_ACCESS_DENIED`를 보고했다. 저장 기록에서 전사와 후보 제안의 성공, 동일 추천 모델의 채점 요청에 대한 HTTP 403을 확인했다. 구체적인 제공자 오류 코드는 남아 있지 않았다. 완료 기준은 실패한 작업의 단계와 이미 저장된 결과를 원래 화면에 표시하고, 새 외부 호출이나 작업을 만들지 않는 것이다.

실패 안내에 처리 단계를 표시하고, 후보 제안이나 채점에서 실패한 작업도 이미 성공한 전사와 표시 자막을 읽어 볼 수 있게 했다. 실제 로컬 프로젝트에서 저장 전사 147개와 자막 미리보기 38개를 확인했다. 표시 품질 기준에 미달해 완성본 SRT는 HTTP 409로 차단됐다. 후보는 0개이며 채점 거부의 상세 원인은 미확인이다. 추가 Groq 호출은 없었다.

격리된 PostgreSQL·Celery·Chromium 통합 검사 14개가 통과했다. 채점 403과 제안 실패 시 저장 전사 조회, 전사 실패 시 조회 차단, 새로고침 시 중복 접수 방지와 다른 사용자 조회 차단을 검사했다. 초기 기본 검사에서 작업 단계가 빠진 테스트 대역 세 건이 실패했고, 실제 전사 단계의 작업 구조를 따르도록 고친 뒤 기본 검사 422개와 Ruff·Alembic을 통과했다. 로컬 Wiki 빌드에서 101개 페이지와 내부 링크 738개를 확인했다. GitHub Wiki에는 게시하지 않았다.

## P4. 분석 대기 화면과 제공자 요청 한도 안내

쇼츠 분석 대기 화면에 진행률 표시를 요청했다. 실제 작업에선 전사와 제안이 성공한 뒤 채점에서 HTTP 429 `rate_limit_exceeded`가 발생했다. 대기 중에는 서버 단계에 맞춰 진행률을 표시하고, 완료와 실패에 맞춰 화면을 전환한다. 새로고침은 기존 작업을 조회하고 실패 안내는 저장된 전사를 다시 보여줘야 한다.

분석 프로젝트 주소에서 단계별 퍼센트와 진행 표시줄을 제공한다. 추천 모드는 대기 0%, 영상 준비 10%, 음성 준비 30%, 전사 45%, 제안 70%, 채점 90%를 사용한다. 전사 전용은 추천 단계를 건너뛰는 비율을 사용한다. 이 수치는 서버가 확인해 준 단계에만 연결된다. 100%는 분석 성공 시 표시한다. 실패하면 대기 영역을 닫고 단계와 오류 안내를 표시한다.

Herdr의 별도 패널에서 표준 검사와 Chromium·워커 검증을 실행했다. 기본 422개와 선택 통합 10개가 통과했다. Chromium에서 단계 갱신, 완료·429 실패 화면 전환, 모바일 화면 너비, 새로고침 중복 방지, 조회 오류 시 다시 확인하는 동작을 검사했다. 실제 로컬 프로젝트에서 429 메시지와 저장 전사 147개가 조회되는 것도 확인했다. 추가 Groq 요청은 보내지 않았으며 남은 한도와 재개 시각은 미확인이다. GitHub Wiki는 미게시다.

## P5. 동일 입력 재실행

사용자 요청으로 같은 자산의 저장 전사를 재사용해 추천을 한 번 다시 접수했다. 새 음성 전사 호출 없이 후보 제안이 성공했고, 제공자가 기록한 제안 사용량은 5,639토큰이다. 후보 채점은 HTTP 403 `PROVIDER_ACCESS_DENIED`로 종료됐다. 제공자의 세부 오류 코드는 없었고 최종 추천 후보는 0개다. 사용자가 승인한 재실행은 이 한 건이며 변경 기록은 로컬에 작성했다.

## P6. 실제 입력 재점검과 제작실 변경 반영

사용자는 별도 패널에서 링크 입력·자막 품질을 확인하고 제작실 변경을 main과 Wiki에 반영해 달라고 요청했다. 기준 커밋은 `edff0cc`다. 동시에 진행 중인 Groq 진단 변경과 겹치지 않도록 별도 작업 트리에 제작실 변경을 복사해 검증했다.

문서의 공개 YouTube 샘플은 Windows 추출 CLI에서 `DOWNLOAD_FAILED`로 종료됐다. 이번 시도에서 원격 응답의 세부 원인은 확인하지 못했다. 공개 MP4 직접 링크는 앞서 개발 워커에서 10.0초 추출에 성공했으나 이번 재검사에서는 워커가 `TIMEOUT`을 반환했다. C 드라이브가 가득 차 작업 트리와 패널 저장이 중단됐고, 공간이 일부 확보된 뒤 분리한 작업 트리에서 반영 절차를 재개했다.

기존 실제 검수본에서는 일부 장면에 원본에 삽입된 자막과 새 자막이 함께 보였다. 현재 출력은 원본 화면을 보존하고, 원본 자막이 확인된 시간 구간에서만 새 영상 자막 표시를 생략한다. 전체 검수 자막은 다운로드용 SRT에 보존된다. 사용자가 추가 영상과 참조 자료가 없다고 확인해 다른 장르의 추천·자막 품질 평가는 보류했다. 이번 확인에서 외부 모델 호출과 SNS 게시는 실행하지 않았다. [실제 검수본 확인](2026-11-18-final-output-e2e.md) · [출력 정책](2026-11-18-flow-output-layout.md).

반영용 작업 트리에서 기존 잠금 환경과 FFmpeg를 재사용해 Ruff, 기본 검사 422개, Alembic 오프라인 SQL을 통과했다. Wiki 생성기는 101개 페이지와 내부 링크 740개를 확인했다. 전체 통합 검사는 반영 PR의 GitHub Actions에서 확인한다.

## P6. Groq 오류 응답 원문 추적

사용자는 응답 본문을 보관해 오류를 추적해 달라고 요청했다. 기본 실행은 정제된 진단을 유지하고, 명시적으로 켠 경우에만 분석 워커의 비공개 저장 공간에 실패 응답 본문을 보관한다. 작업 ID에서 보관 파일을 찾을 수 있어야 하며 앱 응답, 일반 로그와 Wiki에는 원문을 포함하지 않는다. 보관을 검증하고 동일 자산의 새 호출을 추적한다.
