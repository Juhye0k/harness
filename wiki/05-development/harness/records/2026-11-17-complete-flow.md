# 입력부터 편집·출력·업로드까지 연결 — FLOW-001

> 개별 기능을 입력부터 편집·출력·업로드까지 하나의 흐름으로 연결했습니다. 버전 고정과 실제 브라우저 검사에서 발견한 실패, 수정 근거와 검증 한계를 기록합니다.

## 구현 결과

- [편집 API](../../../../app/api/editor.py)와 [편집 화면](../../../../app/static/editor.html)을 추천 후보에 연결했다. 문구·원본 기준 시간·줄바꿈·원음 확인을 별도 버전으로 저장한다. [업무 규칙](../../../../app/domain/caption_edit.py)은 기존 빠른 표시 제약을 유지하며 선택 후보 원 구간의 누락·겹침·범위·제어문자를 거절한다.
- [CaptionRevision](../../../../app/models.py)과 migration `0006_caption_revisions`를 추가했다. [저장소](../../../../app/adapters/caption_repository.py)는 같은 편집본 저장과 동일 버전 출력을 재사용한다. 원본 추출의 후보별 유일성은 유지하고 편집 렌더링은 별도 VideoJob으로 만든다.
- [최종 출력 서비스](../../../../app/services/final_export.py)를 기존 Celery 영상 작업에 연결했다. 원본을 바꾸지 않고 720×1280 MP4와 같은 버전의 클립 SRT를 제공한다. 기존 SNS 확인 흐름에 최종 출력 작업 ID를 전달한다.
- [테스트 전용 리허설](../../../../tests/integration/demo.html)을 제공한다. 상단에 합성 영상·시험음·AI/YouTube 대역임을 계속 표시하며 실제 계정·키를 공유하지 않는다. 별도 로컬 8001 환경으로 실행했고 기존 8000 개발 DB는 전환하지 않았다.

## 목적과 완료 기준

입력 → 다중 추천 → 후보 선택 → 자막 편집·확정 → 비동기 세로 MP4 출력 → 다운로드 → 명시적 확인 후 YouTube 전송을 하나의 웹 흐름으로 연결한다. 모델과 YouTube는 일반 CI의 대역을 사용하고 DB·Redis·Celery·FFmpeg·브라우저는 실제 실행한다. 실제 제공자 품질과 계정 게시 성공을 대역 검사로 대신하지 않는다.

편집본은 원본 전사와 분리한 불변 버전으로 저장한다. 편집 후 이전 결과를 새 편집본의 출력으로 표시하지 않고, 새로고침과 중복 요청은 새 작업·전송을 만들지 않아야 한다. 다른 사용자·후보의 편집본 접근을 거절하며 7일 만료·삭제 경계를 유지한다. 검사 결과·수정 원인·남은 제한은 종료 시 갱신한다.

## 시작 상태와 입력

시작 커밋: `806c1c8d4a45192515e84fd01e68499c86a16cb1`. 기존 전사·자막·인증·추천 평가와 문서의 staged/unstaged/untracked 변경이 있으며 보존한다. 시작 커밋만으로 작업 상태가 재현되지 않는다. 원본·토큰·실행 로그는 공개 문서에 넣지 않는다. 모델·사용량·개발 비용은 알 수 없음이다.

### P1 — 요청 원문 발췌

> 일단 시작부터 끝까지 하나의 플로우를 완성한다음에, 엔드투엔드 테스트를 진행하면서 하네스를 개선해보자

사용자는 개별 품질 개선보다 전체 사용자 흐름 연결을 우선했다. AI는 저장·렌더링·웹 연결을 구현하고, 완료 흐름에서 발견한 실패를 회귀 검사와 완료 기준에 반영한다. 실제 외부 AI 추가 호출과 신규 계정 게시는 실행하지 않는다.

## 실패 발견과 하네스 개선

| 관측·발견 | 원인과 수정 | 재발 방지 |
|---|---|---|
| 첫 E2E에서 자막 저장 422 | 추천용 최소 전사에는 단어 시간이 없어 긴 문장이 편집 초안으로 들어왔다. 후보 ID로 저장 전사 버전의 단어 정보를 읽도록 수정 | `test_complete_flow.py`가 실제 저장·출력까지 수행하며 `test_caption_versions.py`가 자동 초안 품질도 확인 |
| 코드 검토 중 출력 접수와 편집 경쟁 발견 | 요청 대기 중 입력을 바꾸면 이전 버전 결과를 새 내용처럼 보여줄 가능성이 있었다. 접수 중 편집 입력을 잠그고, 이후 편집 시 이전 결과·SNS 링크를 숨김 | POST 응답을 보류한 브라우저에서 입력·저장 잠금을 검사하고 응답을 이어 완료까지 확인 |
| 삭제 검사에서 410 기대와 404 불일치 | 제품 오류가 아니라 검사 시점의 잘못된 기대였다. 삭제 접수 후에는 자산이 남아 410, 정리 후에는 부모 분석이 제거돼 404 | 두 시점을 각각 엄격하게 검사. `404 또는 410`으로 assertion을 완화하지 않음 |
| 리허설 iframe의 SNS 화면 차단 | 기존 SNS `frame-ancestors 'none'`이 프레임을 차단했다. 테스트 전용 `SHORTFORM_DEMO=1`일 때만 같은 출처 프레임을 허용 | 일반 앱의 `/demo` 404·일반 SNS의 none 유지와 호스트 리허설 전체 흐름을 별도 확인 |
| 다른 작업의 파일 추가 중 기본 검사 정적 오류 | 같은 작업 폴더의 제공자·업로드 기능이 계속 변경됐다. 관련 없는 코드를 임의 수정하지 않고 최종 실행 소스를 스냅샷으로 고정 | 앱·테스트·스크립트·잠금 파일 지문을 확인한 격리 실행과 별도 보고서 사용 |

[E2E 검사](../../../../tests/integration/test_complete_flow.py)는 원본 전사 보존, 실제 MP4 다운로드, 출력과 대역 전송 바이트의 SHA-256 일치, 사용자 확인 전 전송 없음, 중복 클릭·새로고침·조회 오류 복구를 검사한다. [버전·권한 검사](../../../../tests/integration/test_caption_versions.py)는 동시 요청 4개가 한 작업을 만드는지, 확인 전 출력 차단·다른 후보/사용자 접근·삭제 시 자막 제거를 검사한다.

성공·실패마다 다른 실행 폴더에 trace·화면·요약을 남긴다. [CI](../../../../.github/workflows/ci.yml)는 기존 integration 안에서 전체 흐름을 실행하고 정리 전에 합성 증거를 수집해 7일 보관하도록 변경했다. 합성 MP4는 CI archive에서 제외하며 실제 사용자 원본·토큰·전사 trace는 게시하지 않는다. 기존 `contents: read` 권한과 실패 판정은 유지했다.

## 포트폴리오용 요약
