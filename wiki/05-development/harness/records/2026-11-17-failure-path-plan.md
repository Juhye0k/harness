# 실패 경로 E2E 계획 — FAIL-E2E-001

> 분석·렌더링 실패와 응답 유실·워커 종료를 어떻게 검사할지 정한 뒤 구현했습니다. 초기 계획과 최종 통합 검증을 구분해 실패 처리 계약의 근거를 설명합니다.

**분석·자막 저장의 응답이 끊겨도 기존 작업으로 복원하고, 실패·중단 때 중복 실행을 막도록 보완했다.** 기본 375개·실제 인프라 통합 107개·컨테이너 강제 종료 3개를 통과했다. 실제 모델 품질과 실계정 게시를 검증한 결과는 아니다.

## 어떤 순서로 해결했나

1. 기존 상태 계약을 확인하고 통신 오류·처리 실패·프로세스 종료를 구분했다.
2. 분석 접수 번호를 보관해 응답 유실 후 같은 작업을 조회하도록 바꿨다.
3. 저장 응답이 유실된 자막은 최신 저장 내용과 비교해 정확한 편집본으로 복원했다.
4. 장애를 단계별로 주입해 DB 상태·화면·파일·실행 횟수를 확인했다.
5. 실제 워커·API를 종료하고 관리자 확정 뒤 늦은 완료와 재전송이 차단되는지 검사했다.

## P1 — 계획 당시 요청과 완료 기준

요청 원문 발췌:

4번은 직전 목록의 분석 실패·통신 끊김·렌더링 실패·워커 중단 등 실패 경로 검사다. 기존 미커밋 FLOW-001·업로드·추천 개선과 문서 변경을 보존했다. 시작 Git 이력은 `94f2474`이며 현재 전체 코드는 미커밋 변경을 포함한다. 정확한 모델·개발 사용량·비용은 알 수 없음이다.

완료 기준은 기존 실패 계약·회귀 검사를 확인하고 추가 시나리오·제품 보완·검사 계층·파일·수행 순서·완료 판정을 구체화하는 것이다. 사용자 직접 구현·결과 검수는 미확인이다. 이번 요청으로 제품 코드나 장애 실험을 실행하지 않는다.

## P1 — 조사와 결정

실제 jobs/analysis/SNS 저장소·워커 서비스·편집 화면·기존 통합 검사를 읽었다. 기본 단일 선점·수동 중단 확정·조회 오류·SNS unknown 검사는 이미 있다. 추가 핵심은 접수 후 응답 유실과 실제 워커 종료다.

분석 등록에는 클라이언트 요청 ID 기반 재사용이 없다는 차이를 확인했다. 계획에 사용자 범위의 receipt·입력 해시·상태 재조회 보완을 포함했다. 출력 버전·SNS upload_id로 복원하는 기존 기능을 신규 분석 등록에도 이미 제공한다고 표현하지 않았다.

현재 조기 ACK·자동 재시도 없음 계약을 유지한다. 워커 종료 후 running 잔류를 예상 동작으로 검사하고 실행 중단 확인 후 기존 CLI를 사용한다. SNS는 원격 접수 가능성이 있으므로 관리자 unknown 처리와 기존 세션 조회를 구분했다. 자동 감시·자동 복구는 범위에 넣지 않았다.

## P1 계획 단계의 산출물과 검증

[실패 경로 구현 계획](../../failure-path-testing.md)에 P0 결정적 실패와 P1 격리 프로세스 종료, 장애 위치별 기대 상태·계수·파일·화면, 구현 파일과 CI 분리를 정리했다. `test_failure_paths.py`, `test_analysis_request_recovery.py`, `run_failure_drills.py`는 계획한 파일이며 아직 만들지 않았다.

추가·수정 문서의 상대 링크 50개가 모두 존재함을 확인했다. 기존 `fail_job --analysis`와 `mark_upload_unknown --worker-stopped` 인자, 상태 전이와 회귀 검사 이름을 실제 코드와 대조했다. `uv run python scripts/verify.py --report <별도 경로>`는 Ruff·서식·기본 **369개**·Alembic 오프라인 SQL을 통과했고 integration 94개를 제외했다. 기존 Starlette/httpx 사용 중단 예정 경고 1건이 남는다. 이는 현재 기본 검사의 결과이며 계획한 새 실패 검사를 실행했다는 뜻이 아니다.

제품 변경이 없어 실제 인프라 강제 종료·새 실패 E2E·외부 AI·SNS·사용자 자료 삭제는 수행하지 않았다. 커밋·푸시·Wiki 게시도 실행하지 않았다.

## P1 계획 단계의 사람·AI 기여와 포트폴리오 요약

사용자는 실패 경로 검증을 다음 설계 대상으로 선택했다. AI는 현행 상태 계약을 조사하고 응답 유실의 멱등성 공백, 오류 표시와 업무 실패의 차이, 프로세스 종료 이후의 관리자 절차를 구체화했다. 본 작업은 구현 성과가 아닌 구현 전 설계 근거이며 품질·생산성 향상률을 측정하지 않았다.

## P2 — 구현 요청

사용자 요청 원문: “진행해”. 기존 계획의 접수 receipt·실패 E2E·격리 프로세스 종료·CI·기록을 구현한다. 시작 HEAD는 `94f2474`이며 기존 FLOW-001·업로드·추천 작업은 보존한다. 제품 외부 AI·실제 SNS·개발 볼륨 삭제는 실행하지 않는다. 실행 결과는 완료 시 갱신한다.

### 구현 결과와 실패 수정

분석 요청에 소유자 범위의 UUID receipt·입력 해시·7일 조회 보장·삭제/만료 표식을 추가했다. 같은 요청의 동시 등록은 같은 분석을 재사용하고 다른 입력은 409로 거절한다. 응답 유실 시 브라우저는 같은 키의 GET 조회로 복원하며 자동 POST를 하지 않는다. 명시적인 재접수도 같은 키를 사용한다. 접수 행과 분석은 같은 DB 트랜잭션이지만 Redis 발행까지 원자적인 것은 아니다.

자막 저장 요청을 응답 확인까지 보관하고, 기존 저장본 URL에서 새 저장 응답이 유실돼도 최신 저장 내용과 비교해 정확한 편집 버전을 복원한다. JSONB 객체 키 순서 차이는 필드 순서를 고정한 비교로 처리했다. 일치하지 않으면 편집 내용을 보존하고 사람이 저장하도록 한다. 처음에는 기존 URL이 이전 버전을 가리키는 경우를 놓쳤고 이 조건을 브라우저 회귀 검사에 추가했다.

하네스에는 작업별 장애·호출 계수·준비 신호, 브라우저 trace·화면·요청 목록, 실패 E2E 13개와 호스트 전용 강제 종료 제어기를 추가했다. 제품 코드에서 테스트 장애 함수를 import하지 않는다. 제어기는 자신이 생성한 전용 Compose 프로젝트·볼륨만 사용하고 컨테이너 중단을 확인한 후 기존 관리자 CLI를 실행한다. 일반 integration CI는 실패 E2E를 포함하며, 실제 프로세스 종료 CI는 수동 실행으로 분리했다.

검증 중 발견한 문제와 조치:

- 키 없는 기존 접수 경로에서 설정 확인보다 repository 메서드 접근이 먼저 일어나던 순서를 수정했다. 비활성 제공자는 기존처럼 DB 사용 전 거절한다.
- 오래된 캐시 이미지의 `/uploads` 권한과 `compose.integration.yaml` 부재로 첫 전체 통합 106개 중 2개가 실패했다. 현재 Dockerfile의 디렉터리 소유권을 반영한 테스트 전용 이미지와 읽기 전용 설정 마운트로 수정했고 assertions는 유지했다.
- 첫 강제 종료 실행은 영상·API 두 시나리오를 통과한 뒤 SNS 단계 API 기동이 40초를 넘어 실패했다. 격리 API의 준비 상한을 90초로 바꾸고 일반 suite와 순차 실행한다. 제품 처리 timeout이나 재시도 정책은 변경하지 않았다.
- 중간 전체 검사에서 Docker 연결 EOF와 컨테이너 비정상 종료가 발생했다. 해당 실행은 통과로 계산하지 않았고 증거를 보관한 뒤 전용 환경을 다시 만들었다.
- 강제 종료 재검사에서 SNS probe 접수 직후의 unknown을 최종 상태로 읽던 테스트 대기 경쟁이 드러났다. 작업 파일의 수정이 고정 스냅샷에 누락돼 있었고, 실제 실행용 파일을 동기화해 probe 완료의 succeeded/failed까지 기다리도록 했다. unknown 상태 검사와 전송 1회 assertion은 유지했다. 해당 실패 실행도 테스트 자원을 모두 정리했다.

### 검증 근거

기본 검사는 `uv run python scripts/verify.py`의 Ruff·서식·**375개**·Alembic 오프라인 SQL을 통과했다. 최종 실제 PostgreSQL·Redis·Celery·FFmpeg·Chromium 통합은 **107개 통과**, 375개 제외, 237.39초다. 기존 Starlette/httpx 사용 중단 예정 경고 1건이 있다. `app_sha256`은 `328e891061e395e23d8563eafba7028a1d1f967b80917c31f7834108e28299bb`이며 기본 검사·고정 소스·현재 앱이 일치한다. 통합 실행 로그와 JUnit·합성 trace는 로컬 `.artifacts/`에 보관한다. 작업 중 동시 수정 영향을 피하려고 `.tmp/fail-e2e-001/source`의 읽기 전용 코드 스냅샷으로 실행했다.

최종 실제 강제 종료 **3개 모두 통과**했다. 실행 `f6dbb3969ae84d95b92e8265c0d23ed2`, 생성 프로젝트 `shortform-failure-8a7c6dcc1907`, 결과 `.artifacts/failure-drills/f6dbb3969ae84d95b92e8265c0d23ed2/result.json`의 `passed`와 `cleanup`이 모두 true다.

| 종료 지점 | 검증 결과 |
|---|---|
| 영상 워커 선점 직후 | 관리자 확정 후 failed/INTERRUPTED, 실행 1회, 늦은 완료 거절 |
| 분석 메시지 발행 후 API 커밋 전 | 관리자 확정 후 failed, provider_calls 0회, 늦은 완료 거절 |
| SNS 대역이 전송을 받은 후 워커 종료 | 관리자 unknown 확정 → 기존 세션 probe → succeeded, 전송 1회·조회 1회, 늦은 완료 거절 |

실제 AI 제공자·실계정 SNS·운영 DB·사용자 영상은 호출하지 않았다. 개발 DB에 migration을 적용하거나 개발 데모를 재배포하지 않았다. 원격 CI 결과도 미검증이다. 관련 문서의 상대 링크 140개와 Git diff 공백 검사를 확인했다.

### 사람·AI 기여와 남은 제한

사람은 실패 경로 검증을 다음 범위로 선택하고 구현 진행을 승인했다. AI는 접수/저장 응답 유실의 제품 보완과 합성 장애 하네스·검사·문서를 작성하고 실행 실패를 진단했다. 모델명·사용량·비용·개발 시간은 도구가 측정값을 제공하지 않아 알 수 없음이다. 내부 추론은 기록하지 않는다.

자동 감시·자동 실패 확정·자동 재시도는 추가하지 않았다. pending/running 중단은 관리자가 실행 주체의 종료를 먼저 확인해야 한다. 실제 발화·추천 품질과 편집한 영상의 실계정 게시 품질은 후속 검증이다. 포트폴리오 근거는 접수 응답 유실과 실제 프로세스 중단을 구분하고, DB 상태·화면·원본 해시·호출 횟수를 실행 검사로 연결한 점이다. 품질 개선률이나 생산성 향상 수치는 측정하지 않았다.
