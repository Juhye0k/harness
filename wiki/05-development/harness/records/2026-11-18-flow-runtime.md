# 기존 실행 환경 복구 — FLOW-RUNTIME-003

> 기존 개발 서비스를 main `45739f4`와 DB `0009`로 복구했다. 두 포트와 API·워커 코드 일치, 백업 대비 기존 테이블 19개·원본·편집 이력 보존을 확인했고 기본 검사 421개를 통과했다. 아래 중단·승인 대기는 과거 경과이며, 최종 복구 결과는 마지막 절에 있다. 사람의 원음 확인과 실제 게시 승인은 후속이다.

## 요청과 완료 기준

별도 작업 트리에서 기존 Compose 프로젝트를 복구하고 PostgreSQL·Redis·API·영상·분석·SNS 워커의 상태를 확인한다. 실제 원본과 편집본을 조회할 수 있어야 한다. 처음에는 병합 전 PR 적용을 계획했으나 최신 사용자 지시에 따라 검증된 코드는 먼저 병합했다. 이 후속 작업은 필수 CI를 통과한 main과 실제 실행 코드를 대조하고 4·5번에 인수하는 범위다.

## 최초 시작 상태와 복구 이력

전용 작업 트리는 깨끗했고 시작 커밋은 `12673d88f8b1fa5a5cc5cd808781d3afd305e0d4`였다. Docker Desktop의 Linux 엔진 연결과 8003 응답이 끊겨 있었다. 설치된 Docker Desktop을 실행해 엔진에 연결했고, 기존 프로젝트 컨테이너와 볼륨을 그대로 사용했다. 제품 코드 변경은 없다.

PostgreSQL과 Redis를 먼저 기동했다. DB의 작업 상태와 Redis 대기열이 비어 있음을 확인한 뒤 API와 세 워커를 기동했다. 새 모델 호출, SNS 게시, 원음 확인 처리 없이 점검했다.

## 최초 인수 뒤 중단됐던 상태

2번과 4번에 기존 런타임 상태를 전달했다. 3번의 `0009_caption_render_jobs`는 기존 스키마 뒤에 렌더 작업을 연결하는 테이블을 추가한다. 실제 적용 전 검증용 PR 커밋에서 다시 확인한다. 유지보수 시 DB·브로커·워커 상태를 재조회하고, 마이그레이션이 필요하면 비공개 백업을 검증한 뒤 적용한다. 필수 CI를 통과한 검증용 PR 커밋을 기다리는 중이다. 호스트의 C 드라이브 여유가 약 1.6MB로 떨어져 새 셸 기동이 실패했다. 이후 두 포트의 생존 점검은 HTTP 200이었으나 DB·Redis 연결이 끊겨 준비 상태는 HTTP 503이었다. 대상 프로젝트의 Docker 상태 조회는 12초 제한 안에 응답하지 않았다. 마지막 호스트 여유 공간은 약 8MB였다. 원인은 확인 중이며 DB 백업이나 마이그레이션을 시작하지 않았다.

## 기록과 게시

- 개발 에이전트 모델·사용량·비용은 확인할 수 없다.
- 사용자가 작업 범위와 원음 확인·SNS 게시 경계를 정했다. Docker 기동과 기존 컨테이너 복구 순서는 에이전트가 선택했다.
- 최초 로컬 기록을 작성했다. 후속 main·Wiki 게시 결과는 [재개 기록](2026-11-19-flow-resume.md)과 완료 보고에서 확인한다.

## 11월 19일 재개

사용자의 최신 요청에 따라 검증을 마친 코드와 상태 문서의 main·Wiki 반영을 진행한다. 2번이 전달하는 필수 CI 통과 PR 커밋 또는 main 커밋을 기존 개발 환경에 적용하고 4·5번에 인수한다. 기존 Docker 프로젝트와 원본·편집 자료의 복구를 먼저 확인한다.

재개 시 C 드라이브 여유 공간은 약 8.16 GiB였다. 설치된 Docker Desktop을 처음 시작했을 때 WSL 배포판 목록 조회가 시간 초과됐다. WSL 조회 응답을 확인한 뒤 Docker Desktop을 다시 시작해 Linux 엔진에 연결했다. 마지막 확인에서 C 드라이브 여유 공간은 약 6.78 GiB였다.

읽기 전용 조회에서 PostgreSQL·Redis·API·세 워커의 기존 컨테이너가 중지 상태였고, PostgreSQL·Redis·영상·업로드 볼륨 네 개가 남아 있었다. 보관한 원본 파일의 SHA-256은 기존 값과 일치했다. SNS 활성화 설정, 기존 키의 존재, 8001 콜백 기준 주소를 값 공개 없이 확인했다. 8003·8001에 HTTP 응답이 없으므로 실제 DB 편집 버전, 계정, 대기열, HTTP 원본은 서비스 재기동 후 확인한다. 취소된 컨테이너 시작은 재시도하지 않았고 백업과 마이그레이션도 대기 상태다.

[main CI](https://github.com/Juhye0k/short-form/actions/runs/44461478341)에서 `45739f449a5c46a0f24a80aea6b8ccd81809d713`의 `checks`와 `integration` 통과를 확인했다. 로컬 Git에서 최종 PR head와 파일 트리가 같음을 대조했다. `0009_caption_render_jobs`는 `0008_analysis_requests` 뒤에 렌더 작업 테이블을 추가하며 이 변경에 의존성이나 Compose 설정 변경은 없었다. 새 승인 뒤 기존 작업과 대기열을 확인하고 DB 백업을 검증한 후 정확한 main을 적용한다.


PR #15의 이전 head `b968ff5`는 Linux 자막 픽셀 검사에서 checks가 실패하고 integration을 통과했다. 이 결과는 11월 19일 최종 PR·main의 CI 통과 기록으로 대체됐다. 이 로컬 복구 기록의 후속 내용은 Wiki에 게시되지 않았다.


## 11월 19일 역할 1 복구 완료 및 인수

기존 개발 런타임을 복구해 역할 4·5에 전달했다. 중지 상태에서 Docker Desktop을 정상 시작하고 기존 PostgreSQL·Redis를 먼저 기동했다. 실제 DB에 0009_caption_render_jobs와 해당 테이블이 이미 있어 마이그레이션을 재실행하지 않았다. 영상·분석·업로드·SNS의 활성 작업과 Redis 우선순위별 대기열·미확인 작업이 모두 0임을 확인한 뒤 기존 API와 워커 세 개를 시작했다.

기존 비공개 PostgreSQL 백업(60,100바이트)을 pg_restore로 끝까지 읽고 백업의 0008과 현재 0009를 대조했다. 버전 테이블을 제외한 기존 테이블 19개의 열과 모든 행이 일치했다. 기존 편집 버전 4개, SNS 계정 1개, 업로드 이력 1개가 보존됐다. 원본 영상의 HTTP 응답 SHA-256도 기존 값과 일치했다.

전용 트리 HEAD와 origin/main은 모두 45739f449a5c46a0f24a80aea6b8ccd81809d713였다. API와 워커 세 개의 앱 SHA-256이 이 트리와 일치했다. 8003·8001의 live와 ready가 모두 HTTP 200이었고 워커 세 개에서 실행·예약·지연 작업이 모두 0건이었다. 역할 4에 편집기와 기존 29개 자막 버전을 인수했고, 역할 5에 8001을 인수했다. 34개 초안의 사람 원음 확인과 실제 게시 승인은 각 역할의 후속 절차다. 이 기록은 로컬 Wiki 원본이다.
복구 후 동일 main에서 기본 검사를 다시 실행해 Ruff·서식·기본 테스트 421개·Alembic 오프라인 SQL을 통과했다. 실제 인프라는 위의 대상 런타임에서 검사했다. 격리 통합 테스트 110개는 동일 커밋의 기존 CI 통과 기록을 사용했다.
