# 최신 코드를 실행하는 독립 개발 환경 — RUNTIME-001

> 코드가 main에 있어도 실행 중인 환경에 적용됐다는 뜻은 아닙니다. 개발 실행 환경 반영과 상태 확인, 실제 품질·운영 배포와의 차이를 기록합니다.

**기존 데이터는 보존하고, 최신 앱을 별도 개발 환경에서 실행해 실제 영상 검증을 준비한다.** API·DB·워커가 같은 코드를 사용하고 필요한 DB 구조까지 갖췄는지 확인하는 작업이다.

## 이번 작업의 목적

기능 검사에 통과한 코드와 실제 개발 서버의 코드가 다르면 사용자는 이전 기능을 보게 된다. 최신 편집·파일 입력·접수 복원 기능을 실제 브라우저에서 검증하려면 실행 환경도 같은 버전으로 맞춰야 한다.

사용자 요청은 “1,2,3번 별도 워크트리 만들어서 작업 진행”이다. 이 문서는 그중 2번 실행 환경 반영을 기록한다. 1번 코드 통합과 3번 실제 영상 검증은 각각 별도 작업으로 진행한다.

## 진행 순서

1. 기존 서버의 데이터와 DB 버전을 확인한다.
2. 원래 환경을 수정하는 대신 새 DB·저장소·대기열을 만든다.
3. 새 DB에 migration을 적용하고 최신 API·워커를 실행한다.
4. 상태 점검·코드 일치·파일 접근 권한을 검사한다.
5. 실제 영상 검증 담당자에게 주소와 접근 방법을 전달한다.

## 시작 상태와 보호 범위

- 시작 코드: `1818e5c` — PR #8의 최신 기능 통합 코드.
- 독립 브랜치: `chore/runtime-release-20261118`.
- 기존 개발 DB는 `0004_transcript_reviews`다. 읽기 전용 SQL로만 확인하며 migration을 적용하지 않는다.
- Docker 엔진 중단 후 기존 개발 컨테이너가 종료된 상태였다. 기존 영상·DB 볼륨을 삭제하거나 초기화하지 않는다.
- 새 환경은 `shortform-release-runtime` 프로젝트이며 기존 DB·Redis·영상 볼륨과 공유하지 않는다.
- 유료 AI·실제 SNS 업로드와 신규 외부 모델 호출은 비활성화한다. 실제 검증은 보존한 결과 재사용을 우선한다.

## 실행 결과

최신 실제 앱은 **http://localhost:8003**에서 실행한다. 추천 화면은 `/recommendations`, API 문서는 `/docs`다. 테스트용 `/demo`는 404로 접근할 수 없다. 기존 개발 환경의 데이터는 그대로 보존했다.

| 확인 항목 | 실제 결과 | 의미 |
|---|---|---|
| API 생존·준비 점검 | `/health/live` 200, `/health/ready` 200 | API 응답과 PostgreSQL·Redis 연결 정상 |
| DB 구조 | `0008_analysis_requests` | 편집 버전·로컬 업로드·접수 복원 테이블 준비 |
| 영상·분석 워커 | 두 워커의 Celery ping 응답 | 올바른 독립 대기열에 워커가 연결됨 |
| 실행 코드 일치 | API·영상 워커·분석 워커의 앱 SHA-256 동일 | 서로 다른 버전의 코드로 처리하지 않음 |
| 파일 접근 | API의 영상 저장소 쓰기 거절, 업로드 저장소 쓰기 허용, 워커 영상 쓰기 허용 | 원본·결과 접근 경계를 실행으로 확인 |
| 영상 도구 | FFmpeg 5.1.9, 한글 Noto CJK 폰트 존재 | 새 출력에 필요한 도구 준비 |
| 기존 DB 보존 | 버전 0004, 성공 분석 5개·실패 15개 유지 | 원래 DB에 migration·작업 쓰기 없음 |
| 외부 부작용 | AI·SNS 비활성, 비밀키 주입 없음 | 환경 기동으로 모델 호출이나 게시가 발생하지 않음 |

### 무엇을 어떻게 실행했는가

일반 production 이미지 위에 워크트리의 `app/`, `migrations/`, `alembic.ini`를 읽기 전용으로 연결했다. API와 워커는 같은 소스를 읽으며 파일은 새 프로젝트의 독립 볼륨에 저장한다. PostgreSQL·Redis는 호스트 포트를 열지 않고 API만 localhost 8003에 공개한다.

실제 실행 구성은 Git에서 제외된 `.artifacts/runtime-release/compose.json`에 보관한다. 환경을 다시 시작할 때는 이 작업을 수행한 워크트리에서 다음 명령을 사용한다.

```powershell
docker compose -f .artifacts/runtime-release/compose.json up --no-build -d api worker analysis-worker
docker compose -f .artifacts/runtime-release/compose.json ps
curl.exe http://localhost:8003/health/ready
```

종료할 때는 같은 구성에 `down`만 사용한다. 사용자 영상이 들어온 뒤에는 `down --volumes`를 실행하지 않는다. 새 DB의 스키마 사본은 비공개 로컬 산출물에 보관했다. 원래 DB에 migration을 하지 않았으므로 원래 데이터 복구를 전제로 한 변경은 없다.

### 검사 근거와 실제 영상 검증의 경계

제품 코드는 변경하지 않았다. 시작 코드 `1818e5c34a7ae9df3b71cc56b37f97706267e5a0`의 [원격 CI](https://github.com/Juhye0k/short-form/actions/runs/44109476310)에서 기본 375개·통합 107개·Ruff·서식·Alembic SQL 검사가 통과한 근거를 재사용한다. 이 작업에서는 위 표의 실제 실행 환경 검사를 추가했다. 동일 코드를 대상으로 의미 없는 업무 테스트를 새로 만들지 않았다.

실행 앱 SHA-256은 `8ed6682fec350f36669c8cced80f4902b451d3fe2056e5f9187045bd454d48e7`이다. 앱을 변경하면 다시 계산해 비교해야 한다. 이미지 ID는 로컬 산출물에 남겼다.

3번 담당자에게 같은 주소와 저장소를 전달했다. 해당 담당자는 일반 웹의 파일 입력으로 실제 원본을 업로드하고, 승인된 과거 전사·추천 결과를 새 자산에 연결해 검증한다. **기존 실모델 결과를 재사용하는 검증과 새 모델을 호출하는 검증은 구분한다.** 자막의 의미·원음 일치에 대한 사람의 확인과 실제 SNS 게시까지 끝났다는 뜻도 아니다.

## 남은 제한

- 운영 배포·외부 공개·다중 서버 저장소 구성은 아니다.
- Google 로그인을 끈 localhost 전용 개발 환경이다. 기존 인증·계정 데이터는 복제하지 않는다.
- 새 AI 호출·실제 SNS 게시·사용자 데이터 삭제는 수행하지 않는다.
- 원본 개발 서버의 8000 포트는 전환하지 않았다. 이번 검증에서는 8003을 사용한다.
