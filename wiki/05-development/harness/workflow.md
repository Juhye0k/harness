# AI와 함께 작업하는 개발 하네스

> 상태: 현재 개발 절차 · 기준일: 2026-11-15 · 유지관리: 프로젝트 개발자

[위키 홈](../../README.md) · [하네스 목차](README.md)

## 하네스의 역할

하네스는 사람이든 AI든 같은 환경에서 변경하고 검사하도록 연결한 지침·실행 도구·검증·피드백 체계다. 영상 생성 파이프라인 자체와 구분한다.

`작업 범위·프롬프트 기록 → 코드·문서 읽기 → 최소 변경 → 검사 → 실패 수정 → 리뷰·결과 기록 → 승인 범위의 커밋·CI·Wiki 게시`

| 구성 | 실제 파일 | 의미 |
|---|---|---|
| 작업 지침 | [AGENTS.md](../../../AGENTS.md) | 범위·계층·완료 조건 |
| 환경 | [pyproject.toml](../../../pyproject.toml), [uv.lock](../../../uv.lock) | 의존성 재현 |
| 실행 | [compose.yaml](../../../compose.yaml) | 프로세스·DB·브로커 연결 |
| 검사 | [verify.py](../../../scripts/verify.py), [tests](../../../tests) | 실행 가능한 판정 |
| CI | [ci.yml](../../../.github/workflows/ci.yml) | 다른 환경에서 다시 검증 |
| 리뷰 | [검토 기준](review.md) | 자동 검사로 놓치는 영향 확인 |

## 작업 시작과 종료

1. 현재 작업과 해당 단계의 완료 기준을 확인한다. 의미 있는 작업은 [프롬프트·결과 기록](records/README.md)을 만들거나 기존 작업 기록을 찾아 요청과 시작 상태를 남긴다.
2. [요구사항 연결표](requirements-map.md)와 관련 코드를 읽고 실제 동작과 설계를 구분한다.
3. 변경 범위가 새 기능·외부 서비스 도입까지 넓어지면 원래 요청을 다시 확인한다.
4. 실패를 재현하는 검사가 필요한지 판단하고 의미 있는 검사를 추가한다.
5. 기본 검사를 실행하고 인프라 변경이면 통합 검사도 수행한다.
6. 작업 기록에 프롬프트별 결과·실패와 수정·사람의 결정·검증 근거·포트폴리오 요약을 갱신하고 [목차](records/README.md)에 연결한다. 후속 요청은 같은 기록에 추가한다. 의미 있는 실패 개선은 [개선 기록](changes/README.md)으로 연결하고 상세 내용을 중복 작성하지 않는다.
7. 완료 보고에 제품 변경과 하네스 변경, 검사, 한계, 미실행 이유, 작업 기록 링크와 Wiki 게시 여부를 포함한다. 커밋·푸시·Wiki 게시는 해당 승인 범위에서 수행하고 결과를 기록한다.

## 지침과 강제 장치의 차이

AGENTS.md의 '허용 범위 안에서 작업'은 지침이다. 파일 접근·명령 승인·네트워크 제한은 에이전트 실행 환경이 강제한다. CI의 contents:read 권한은 실제 GitHub 권한 제한이다.

CI 실패를 병합 차단으로 연결하려면 GitHub ruleset이 별도로 필요하다. 현재 파일에 CI가 있다는 사실만으로 병합 보호가 설정됐다고 말하지 않는다.

## 이후 개선

첫 제품 기능인 [링크 기반 10초 추출](../video-extraction.md)은 구간·길이·원본 보존 계약을 실제 FFmpeg 검사에 연결했다. 외부 링크 가용성과 코드 회귀를 구분하기 위해 일반 CI는 합성 영상·다운로더 대역을 쓰고 공개 링크는 별도 실행한다.

같은 실수가 반복되면 원인을 분류한다. 명령을 못 찾으면 문서·진입점을, 잘못된 동작을 못 잡으면 테스트를, 판단 기준이 모호하면 요구·평가 문서를 고친다. 매번 지침만 길게 추가하지 않는다.

스킬·자동 AI 리뷰·MCP는 현재 필수 구성에 포함하지 않았다. 반복 작업이나 연결 필요가 확인될 때 추가한다.
