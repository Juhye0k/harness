# 추천 후보가 한 개만 남은 경로

> 같은 원본의 저장 전사 147구간으로 Groq에 제안과 채점을 요청했습니다. API와 브라우저가 보여 준 결과는 후보 한 개, 52.5점이었습니다. 최종 개수만으로 어느 단계에서 다른 후보가 사라졌는지 알 수 없습니다.

한 번의 분석은 최대 다섯 후보를 반환합니다. 장르와 추천 목적을 받지만 첫 구현의 입력은 대화 전사입니다. 득점 장면처럼 대사 없이 화면에서만 드러나는 사건을 평가할 정보는 없습니다. 먼저 [전사·추천 실행 설정](groq-free-ai.md)에서 제공자와 허용 범위를 확인합니다.

## 후보 수가 달라지는 단계

1. Groq Whisper 또는 Azure Fast Transcription 결과를 `id/start_ms/end_ms/text` 전사로 정규화한다. `transcripts`의 `(asset_id, version)` 고유 제약으로 중복 전사 호출을 막고 제공자·전처리 버전을 분리한다. 진행 중이거나 실패한 전사는 자동 재호출하지 않는다.
2. 선택한 제공자의 제안 호출에 전사와 장르·목적을 전달한다. 최대 15개 구간 ID 쌍을 받고 서버가 시간을 계산한다. 30~60초 범위, 순서, 원본 경계를 검사하고 최대 200ms씩 여유를 추가한다. 최종 60초 상한을 유지한다.
3. 별도 평가 호출로 도입·완결성·독립성·인상·편집성 점수를 각각 0~4로 받는다. 근거 ID가 해당 후보에 속하는지도 검사한다.
4. 서버가 `25/25/20/20/10` 가중치로 100점 점수를 계산한다. 완결성·독립성 2점 미만은 제외한다. 점수 내림차순·시작 시간·후보 ID 순으로 정렬하고 짧은 후보 길이 대비 겹침 50% 이상을 제거한다. 동일 주제는 최대 2개, 최종 최대 5개다.
5. 최종 후보와 분석 성공 상태는 같은 DB 트랜잭션에서 확정한다. `highlight_candidates`에는 제목·구간·전사·근거·세부 점수·순위를 저장한다.
6. 후보 선택 시 `video_jobs`를 만들며 같은 후보의 재요청은 기존 작업 ID를 반환한다. 실패한 출력도 자동 재실행하지 않는다. 파일이 없으면 재다운로드하지 않고 오류로 남긴다.


## 실제 기록을 어디까지 해석할 수 있나

이전 실행에서는 후보가 두 개였습니다. 이번에는 제안·채점 호출 성공과 최종 한 개까지 확인했습니다. 모델이 처음부터 하나만 제안했는지, 점수 하한이나 겹침 규칙에서 줄었는지 복원할 단계별 개수가 없습니다. 다음 실험에서는 같은 입력·설정에서 제안 수, 유효 구간 수, 채점 뒤 제외 사유별 수, 최종 수를 함께 기록해야 합니다. 52.5점은 편집 적합도의 서버 점수입니다. 시청자 반응이나 다른 장르에서의 품질은 사람 평가가 필요합니다.

채점이 거절된 다른 실행에서는 성공한 전사 147구간을 여전히 조회할 수 있었습니다. 실패한 호출을 자동 반복하지 않습니다. 당시 403의 제공자 내부 원인은 미확정이며, 성공한 재추천만으로 그 원인을 특정할 수 없습니다. [개발 제작실의 당시 기록](harness/records/2026-11-20-project-workspace.md) · [선정 규칙 코드](../../app/domain/recommendations.py)
