## 문서 경계

이 문서는 모델링 논의를 위한 초안이다. 현재 SQLAlchemy Base와 Alembic 환경만 있으며 아래 테이블·상태·복구 로직은 구현되지 않았다.

## 논리 모델 제안

| 개체 | 주요 정보 | 관계 |
|---|---|---|
| projects | 소유자 식별자·이름·설정 | 원본·작업을 묶음 |
| assets | 파일 위치·해시·길이·해상도·트랙 | 프로젝트에 속함 |
| jobs | 종류·상태·입력·시도·오류·시간 | 특정 자산/편집 버전 처리 |
| transcripts | 원본 시간 기준 전사 구간·분석 버전 | 원본 자산에 속함 |
| candidates | 시작·종료·특징·점수·추천 이유 | 분석 결과에 속함 |
| clip_revisions | 후보·제목·수정 자막·출력 설정 | 변경 시 버전 구분 |
| exports | 편집 버전·출력 파일·검증 결과 | 확정된 편집 버전을 참조 |
| usage_events | 호출량·처리 시간·비용 추적 | 작업에 연결 |

사용자 인증 주체의 구현 방식은 미정이다. 핵심 관계·상태·시간은 일반 컬럼에 두고 변경이 잦은 분석 특징·설정은 JSONB 후보로 둔다. 대형 원본 응답·프레임·영상은 객체 저장소에 보관하고 DB에는 참조를 남긴다.

## 시간과 버전

구간은 원본 기준 정수 밀리초와 반열린 구간 `[start_ms, end_ms)`를 사용하는 안을 제안한다. 편집 자막은 클립 기준 시간으로 변환하되 원본과의 매핑을 보존한다. DB 시간 단위와 FFmpeg 초 단위 변환은 경계에서 수행하고 검사한다. 아직 이 규칙은 코드 계약으로 확정되지 않았다.

## 상태 전이 제안

`queued → running → succeeded | failed`

재시도는 횟수와 실패 원인을 남긴 후 다시 queued로 전환하는 안을 검토한다. 취소·부분 완료는 요구가 확정된 뒤 추가한다. queued와 broker 발행 여부는 다른 정보이므로 하나의 필드로 덮어쓰지 않는다.

## 작업 전달과 중복

- PostgreSQL 기록과 Redis 발행은 하나의 원자적 트랜잭션이 아니다.
- outbox(작업과 발행 예약을 같은 DB 트랜잭션에 저장) 또는 미발행 작업 재점검 중 초기 방식을 결정해야 한다.
- job_id는 업무 식별자, Celery task_id는 실행 시도 추적용으로 분리하는 안을 권장한다.
- 완료 작업의 재전달과 동시에 실행 중인 작업의 중복 선점을 모두 고려한다.
- 출력은 job_id·편집 버전에 연결하고 오래된 시도가 최신 결과를 덮어쓰지 않도록 검증한다.
- 외부 API 호출은 응답 저장 직전 장애 시 비용이 중복될 수 있다. DB 완료 확인만으로 모든 부작용이 한 번으로 제한되지는 않는다.

## 구현 전 완료할 결정

상태 전이 조건, 작업 선점 방식, 실행 중단 감지, ACK 시점, 재시도 허용 오류·상한, 산출물 저장과 완료 표시 순서. [미결정 목록](../07-governance/open-decisions.md)의 D-04에서 관리한다.
