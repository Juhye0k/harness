# 현재 실행 흐름과 목표 사용자 흐름

> 영상 입력에서 다운로드까지 API·DB·대기열·워커가 어떻게 연결되는지 설명합니다. 현재 실행 가능한 흐름과 객체 저장소·자동 복구 등 아직 없는 기능을 구분합니다.

[위키 홈](../README.md) · [카테고리 목차](README.md)


## 현재: 생존 점검

`클라이언트 → GET /health/live → FastAPI → 200 {status: ok}`

DB·Redis를 호출하지 않는다. 프로세스가 응답하는지 확인하는 경로다.

## 현재: 의존성 점검

`클라이언트 → GET /health/ready → PostgreSQL SELECT 1 → Redis PING → 응답`

두 연결을 순서대로 검사하고 모두 성공하면 200, 하나라도 실패하면 503을 반환한다. 응답에는 구성 요소별 ok/unavailable만 포함한다. 원본 예외나 연결 암호를 반환하지 않는다. 이 경로는 Celery 워커의 생존을 확인하지 않는다.

## 현재: 워커 통합 진단

`검사 프로그램 → Redis → Celery diagnostic_ping → 임시 결과 저장 → 검사 프로그램 확인`

진단 워커만 Redis result backend를 사용한다. 테스트는 결과를 확인한 뒤 해당 키를 삭제한다. 일반 Compose 워커에는 결과 backend가 없다. 테스트와 일반 워커를 동시에 같은 대기열에 연결하면 일반 워커가 메시지를 가져갈 수 있어 진단 시 분리한다.

## 현재: 링크 기반 로컬 추출

`터미널 → URL·시작 시간 검사 → 별도 다운로드 프로세스 → 원본 정보·구간 검사 → FFmpeg 추출 → 길이·트랙·전체 디코딩·원본 해시 검사 → 로컬 MP4·JSON`

CLI는 FastAPI·PostgreSQL·Redis·Celery 없이 독립 실행한다.

## 현재: 비동기 10초 추출

`POST → pending 저장 → Redis 발행·queued 확정 → 202 → Celery 조건부 선점 → running → 기존 추출 서비스 → 검증 → succeeded/failed → GET 조회·다운로드`

메시지를 배분하는 것은 Redis/Celery, 상태를 검증하는 것은 PostgreSQL이다. ID 행 잠금으로 발행과 소비 경쟁을 조정하고 인코딩 중에는 잠금을 유지하지 않는다. [상태 계약](data-and-jobs.md), [실행 안내](../05-development/async-video-jobs.md). 웹 화면과 전사 기반 추천·편집 출력은 구현했다. 아래에서 파일 입력부터 최종 출력까지의 현재 흐름을 설명한다.

## 현재: 로컬 파일 입력과 원본 검증

`업로드 생성 → 파일 바이트 PUT → 수신 크기·해시 기록 → video 큐 → 워커 형식·길이 검사 → 관리 원본 복사 → ready`

API는 별도 수신 볼륨에만 쓰고 관리 원본은 읽기 전용으로 사용한다. 최대 500MiB·20분 파일을 지원하며, 새로고침은 상태만 조회한다. 객체 저장소의 서명 URL 업로드는 아직 없다. [업로드 계약](../05-development/local-video-upload.md).

## 현재: 전사와 후보 선택

`분석 POST → 원본 준비 또는 재사용 → 음성 추출 → 전사 저장 → 후보 제안·서버 점수 계산·중복 제거 → 후보 조회`

현재 추천은 한국어 음성 전사 기반이다. 영상 프레임 특징의 결합은 후속이다. 전사 전용 모드에서는 후보 모델을 호출하지 않는다. 전사 제공자는 기본 Groq이며, 검증한 단어 시각만 표시 자막 분할에 사용한다.

브라우저는 전송 전에 `request_id`를 보관한다. 접수 응답을 잃으면 같은 번호의 GET 조회로 복원하며 새로고침으로 POST를 자동 실행하지 않는다. [API 계약](api-contract.md).

## 현재: 편집본 고정과 최종 출력

`후보 선택 → 원음·자막 확인 → 편집 버전 저장 → 출력 작업 접수 → 워커 세로 렌더링·검사 → MP4·클립 SRT 다운로드`

원본 전사와 편집본은 별개다. 확인한 동일 버전은 기존 출력 작업을 재사용하며 내용을 고치면 이전 결과를 숨긴다. 출력과 전사는 별도의 작업이므로 자막 수정만으로 전사를 다시 호출하지 않는다. [전체 흐름](../05-development/complete-flow.md).

## 현재: 확인한 출력의 SNS 전송

계정·영상 바이트·제목·공개 범위에 묶인 최종 확인 뒤 전용 워커가 전송한다. 전송 결과가 불명확하면 `unknown`으로 보관하고 기존 원격 세션을 조회한다. 자동 재전송은 하지 않는다. [YouTube 실행 안내](../05-development/youtube-upload.md).

## 실패를 숨기지 않는 흐름

요청 거절, 작업 대기, 처리 실패, 출력 만료를 구분한다. 재시도는 실패 단계와 이미 완료된 산출물을 확인한 뒤 수행하도록 설계한다. 현재 상태와 후속 복구 범위는 [데이터·작업 모델](data-and-jobs.md)에 있다.
