# 현재 실행 흐름과 목표 사용자 흐름

> 영상 입력에서 다운로드까지 API·DB·대기열·워커가 어떻게 연결되는지 설명합니다. 현재 실행 가능한 흐름과 객체 저장소·자동 복구 등 아직 없는 기능을 구분합니다.

**사용자의 요청은 API에서 접수되고, 분석·출력은 워커에서 진행된다.** 사용자는 추천 후보와 자막을 확인한 뒤 출력할 버전을 정한다. 이 문서는 한 영상을 처리할 때 각 구성 요소가 무엇을 하는지 순서대로 설명한다.


[위키 홈](../README.md) · [설계 목차](README.md)

## 1. 영상 입력과 원본 준비

사용자가 링크를 입력하거나 로컬 파일을 올린다. 파일 입력은 수신 완료와 영상 검증 완료를 구분한다. 크기·형식·재생 시간 등 검증을 통과한 원본을 이후 분석과 출력에 재사용한다. 원본은 덮어쓰지 않는다.

파일은 전용 볼륨에 저장하며 Redis에는 넣지 않는다. 업로드 요청·실제 바이트·영상 검증의 연결은 [업로드 안내](../05-development/local-video-upload.md)에 있다.

## 2. 분석 작업 접수

브라우저가 요청 번호 `request_id`를 보관한 뒤 분석을 요청한다. API는 입력·소유권을 확인하고 PostgreSQL에 접수 기록과 분석 작업을 저장한다. Redis에 작업 ID를 보내고 접수 결과를 반환한다.

같은 사용자·요청 번호·입력은 기존 분석을 돌려준다. 응답을 못 받아도 새로 만들지 않고 원래 요청 번호로 조회한다. 다른 입력에 같은 번호를 쓰면 거절한다.

## 3. 워커가 전사·추천 생성

Celery 분석 워커가 ID로 작업을 읽고 대기 상태를 실행 상태로 바꾼다. 이 상태 변경에 성공한 워커만 처리한다. PostgreSQL이 워커를 대신하는 것이 아니라 **실행 권한을 한 작업에 한 번만 부여하는 기준**이 된다.

워커는 원본에서 음성을 준비하고 한국어 전사와 시간 정보를 생성한다. 추천 모드에서는 검증한 전사 ID로 후보를 만들고 서버 점수를 계산해 중복 구간을 제거한다. 현재는 대화·텍스트 기반이며 시각 장면 분석은 하지 않는다. 이미 성공한 같은 버전의 전사는 재사용한다.

## 4. 후보 선택과 자막 편집

브라우저가 분석 상태를 조회하고 후보의 구간·점수·근거를 보여 준다. 사용자가 한 후보를 선택하면 저장된 원 전사에서 편집 초안을 만든다.

사용자는 문구·시간·줄바꿈을 수정하고 원음을 확인한다. 단어 시각이 부족한 구간은 자동으로 정확한 짧은 자막을 만들었다고 표시하지 않는다. 편집은 원본 전사와 분리된 버전으로 저장한다.

## 5. 확정 버전으로 영상 출력

확인한 편집 버전으로 출력 작업을 접수한다. 영상 워커가 FFmpeg로 720×1280 세로 MP4와 클립 기준 SRT를 만들고 길이·트랙·디코딩·원본 해시를 검사한다.

검수한 자막 34개를 출력했을 때, 원본에 이미 자막이 찍혀 있는 장면에서 같은 문장이 두 번 보였다. 지금은 편집자가 원본 자막이 보이는 시간대를 지정하면 영상 워커가 그때만 새 자막을 숨긴다. 내려받는 SRT에는 34개가 모두 남는다. 같은 편집 버전과 같은 출력 조건으로 다시 요청하면 기존 출력 작업을 재사용한다. [실제 영상의 전후 비교](../05-development/harness/records/2026-11-18-final-output-e2e.md)

## 6. 다운로드와 SNS 확인

API는 소유권과 성공 상태를 확인한 결과만 내려준다. YouTube로 이동하면 계정·파일·제목·공개 범위를 보여 주고 별도로 게시 동의를 받는다. 자막 확인과 게시 동의는 다른 행동이다.

SNS 전용 워커가 확인한 파일을 전송한다. 전송 결과가 불명확하고 기존 세션이 남아 있으면 그 상태를 조회한다. 실제 보정본 한 건은 YouTube에서 처리가 끝났고 사용자가 Studio의 Shorts 목록에서 확인했다. 이때 파일과 공개 범위는 일치했지만 실제 제목은 사전에 합의한 제목과 달랐다. 다음 개선 대상은 제출 직전 제목 대조다. [게시 검증 기록](../05-development/harness/records/2026-11-18-sns-final-output-validation.md)

## 실패하면 어디에서 멈추나

| 상황 | 서비스의 판단 | 다음 행동 |
|---|---|---|
| 입력 조건 위반 | 접수 전 거절 | 사용자가 입력 수정 |
| GET 조회 통신 오류 | 업무 상태는 그대로 | 같은 작업 다시 조회 |
| POST 응답 유실 | 접수 여부 미확정 | 보관한 요청·버전·업로드 ID 조회 |
| 도구·모델 실패 | 워커가 failed 저장 | 오류 코드와 단계 확인 |
| API·워커 강제 종료 | pending/running이 남을 수 있음 | 관리자가 실행 중단을 확인한 뒤 상태 확정 |
| SNS 전송 결과 미확정 | unknown | 재전송 없이 기존 세션 상태 조회 |

DB와 Redis 발행은 하나의 원자적 트랜잭션이 아니다. 조기 ACK와 자동 재시도 없음이 현재 계약이다. [실패 경로 검사](../05-development/failure-path-testing.md)와 [관리자 절차](../05-development/async-video-jobs.md)를 참고한다.

## 서비스가 준비됐는지 확인하는 방법

- `/health/live`: API 프로세스가 응답하는지 확인한다. DB·Redis를 호출하지 않는다.
- `/health/ready`: PostgreSQL 연결과 Redis PING을 확인한다. 하나라도 실패하면 503이다. 워커 생존을 보장하지 않는다.
- 통합 진단: 실제 큐에 진단 작업을 보내 워커 응답을 확인한다. 제품 작업의 상태는 PostgreSQL을 기준으로 한다.

CLI의 10초 추출은 API·DB·Redis 없이 독립 실행한다. [CLI 실행 안내](../05-development/video-extraction.md)를 따른다. 객체 저장소 업로드·시각 분석·다중 호스트·자동 복구는 후속 확장이다.
