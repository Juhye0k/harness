# 현재 실행 흐름과 목표 사용자 흐름

> 상태: 현재 동작 명세 + 목표 설계 · 기준일: 2026-11-15 · 유지관리: 프로젝트 개발자

[위키 홈](../README.md) · [카테고리 목차](README.md)

## 현재: 생존 점검

`클라이언트 → GET /health/live → FastAPI → 200 {status: ok}`

DB·Redis를 호출하지 않는다. 프로세스가 응답하는지 확인하는 경로다.

## 현재: 의존성 점검

`클라이언트 → GET /health/ready → PostgreSQL SELECT 1 → Redis PING → 응답`

두 연결을 순서대로 검사하고 모두 성공하면 200, 하나라도 실패하면 503을 반환한다. 응답에는 구성 요소별 ok/unavailable만 포함한다. 원본 예외나 연결 암호를 반환하지 않는다. 이 경로는 Celery 워커의 생존을 확인하지 않는다.

## 현재: 워커 통합 진단

`검사 프로그램 → Redis → Celery diagnostic_ping → 임시 결과 저장 → 검사 프로그램 확인`

진단 워커만 Redis result backend를 사용한다. 테스트는 결과를 확인한 뒤 해당 키를 삭제한다. 일반 Compose 워커에는 결과 backend가 없다. 테스트와 일반 워커를 동시에 같은 대기열에 연결하면 일반 워커가 메시지를 가져갈 수 있어 진단 시 분리한다.

## 목표: 입력과 작업 등록 — 미구현

1. API가 소유권·입력 조건을 확인하고 파일 업로드 정보를 제공한다.
2. 브라우저가 서명 URL로 객체 저장소에 업로드한다.
3. 서버가 실제 파일 정보와 요청 조건을 검사한다.
4. DB에 작업을 기록하고 메시지 전달을 예약한다.
5. 작업 ID를 반환하고 UI는 상태를 조회한다.

링크 입력은 지원 출처에서 파일을 가져오는 별도 작업을 거친 뒤 같은 분석 경로로 합류한다. 임의 URL을 무제한으로 가져오도록 설계하지 않는다.

## 목표: 분석과 후보 선택 — 미구현

워커가 작업 ID로 DB와 파일을 조회한다. 음성·프레임·전사문에서 특징을 추출하고 후보·점수·버전을 저장한다. 화면은 상태 API를 통해 후보를 표시하고 사용자가 선택·수정한 내용을 편집 버전으로 저장한다.

분석 완료와 출력 완료는 다른 상태다. 자막 수정은 전사를 다시 실행할 이유가 아니며, 가중치 변경도 기존 특징을 재사용할 수 있어야 한다.

## 목표: 최종 출력 — 미구현

선택한 후보와 편집 버전으로 출력 작업을 등록한다. 워커가 FFmpeg를 실행하고 파일을 검증·저장한 후 DB에 완료를 기록한다. API는 결과 접근 권한을 확인해 다운로드 주소를 반환한다.

## 실패를 숨기지 않는 흐름

요청 거절, 작업 대기, 처리 실패, 출력 만료를 구분한다. 재시도는 실패 단계와 이미 완료된 산출물을 확인한 뒤 수행하도록 설계한다. 자세한 미결정 사항은 [데이터·작업 모델](data-and-jobs.md)에 있다.
