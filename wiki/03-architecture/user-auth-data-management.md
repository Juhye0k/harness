> 상태: 로컬 구현·격리 환경의 실제 Google 로그인 확인 / 초기 계획 보존 · 기준일: 2026-11-17

## 목표와 범위

후속 요청으로 이 계획을 로컬 구현하고 기본 345개·격리 통합 81개를 통과했다. 별도 로컬 환경에서 실제 Google 테스트 계정의 로그인·승인·로그아웃도 확인했다. 실제 설정·기본값·보수적인 사용자 단위 정리 제한과 검증 범위는 [실행 안내](../05-development/user-auth-data.md)를 따른다. 아래는 초기 계획이며 운영 배포 완료를 뜻하지 않는다.

Google로 로그인한 사용자가 본인의 영상·분석·전사·검수·출력·YouTube 연결만 조회하고 관리하게 한다. 로그인 여부를 확인하는 인증과, 해당 자료에 접근해도 되는지 확인하는 소유권 검사를 함께 구현한다. 이 문서는 계획이며 현재 API에 인증·삭제 기능이 적용됐다는 의미가 아니다.

첫 버전은 사용자 한 명이 본인의 자료를 관리하는 구조로 한다. 팀·공유 링크·역할별 관리자 화면, 일반 작업 자동 복구, 객체 저장소 이전, 운영 배포는 별도 범위다. 기존 로컬 파일 저장과 PostgreSQL을 사용한다. 비밀번호 가입·재설정은 Google 로그인 선택에 따라 구현 범위에서 제외한다.

## 로그인과 세션

사용자는 Google 로그인을 선택했다. OpenID Connect(OIDC, 로그인 결과로 사용자 신원을 확인하는 표준)의 서버 코드 교환 흐름을 사용한다. 로그인 권한은 `openid email`로 시작하고 YouTube 업로드 권한은 사용자가 별도로 연결할 때만 요청한다. 로그인용 클라이언트 설정·콜백과 기존 YouTube 설정을 분리한다.

로그인 요청마다 일회성 state·nonce·PKCE 검증값과 만료를 저장하고 시작한 브라우저에 연결한다. 콜백에서 state를 한 번만 소비하고, ID 토큰 서명·발급자·대상 클라이언트·만료·nonce를 검증한다. 검증된 `issuer + sub`를 외부 계정 식별자로 쓰며 이메일로 계정을 합치지 않는다. Google은 이메일 대신 sub를 식별자로 사용하도록 안내한다. [Google OIDC 문서](https://developers.google.com/identity/openid-connect/openid-connect), 확인일 2026-11-17.

검증된 OIDC 라이브러리를 구현 단계에서 선정한다. 기존 의존성에는 OIDC 클라이언트가 없으므로 토큰 검증을 직접 재구현하기보다 검증 기능을 제공하는 최소 의존성 하나를 검토하고 이유·uv.lock을 함께 반영한다. 새 인증 서버나 유료 서비스는 추가하지 않는다.

앱 세션은 충분히 무작위인 토큰을 쿠키로 전달하고, PostgreSQL에는 토큰 해시·user_id·만료·폐기 상태를 저장한다. 로그인 성공 시 새 토큰을 발급하고 로그아웃하면 서버에서 무효화한다. 쿠키는 HttpOnly·SameSite=Lax·Path=/, 운영 HTTPS에서는 Secure·host 전용으로 설정한다. 로컬 HTTP 예외는 development/test에만 허용한다. 세션 유휴 24시간·절대 7일은 초기 정책안이며 UI 상태 조회만으로 유휴 기한을 연장하지 않는다. [OWASP 세션 관리](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), 확인일 2026-11-17.

업무 변경 요청에는 세션에 묶인 CSRF 토큰과 설정한 Origin 검사를 적용한다. CSRF는 다른 사이트가 사용자의 로그인 상태를 이용해 변경 요청을 보내는 공격이다. 쿠키의 SameSite만으로 대체하지 않는다. 콜백은 별도의 일회성 로그인 검증 흐름으로 다룬다. 리다이렉트 복귀 경로는 앱 내부 허용 경로만 받는다. [OWASP CSRF 지침](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html), 확인일 2026-11-17.

로그인용 Google 토큰은 검증 후 장기 보관하지 않는다. YouTube 전송에 필요한 토큰은 기존 암호화 보관을 유지한다. 콜백의 code·토큰·쿠키는 앱과 접근 로그에 남기지 않는다.

## 데이터와 접근 규칙

| 대상 | 변경안 |
|---|---|
| users | 내부 UUID, 활성/탈퇴 처리 상태, 생성 시각. 화면에 필요한 최소 정보만 저장 |
| auth_identities | user_id, provider, issuer, subject. issuer+subject 유일 제약 |
| auth_sessions / auth_login_states | 세션 해시·만료·폐기, 일회성 로그인 상태·브라우저 결합 정보 |
| assets | user_id, created_at, expires_at, 삭제 상태. 새 자료는 소유자 필수 |
| video_jobs | user_id, expires_at, 삭제 상태. 후보 출력은 부모 원본 소유자를 상속 |
| analysis_jobs·transcripts·candidates·reviews·provider_calls | 부모 원본 또는 분석과의 관계로 소유권을 추적 |
| sns_accounts·sns_uploads·sns_oauth_states | user_id로 연결. 브라우저 세션 해시를 영구 소유자로 사용하지 않음 |
| deletion_requests | 대상·사용자·접수/진행/실패/완료 상태·정제된 오류·시각. 파일 경로는 서버가 결정 |

API 입력으로 user_id를 받지 않고 인증된 세션에서 정한다. 저장소 조회도 `get_owned(...)`처럼 사용자 조건을 필수로 받게 하고, 권한 없는 조회가 상세 데이터를 읽은 뒤 걸러지는 구조를 피한다. 원본 재사용·후보 출력 생성은 같은 트랜잭션에서 부모 소유권·삭제 상태를 확인한다. 워커 내부 조회는 외부 요청용 조회와 구분하되 작업에 저장된 소유자와 현재 사용 가능 상태를 검사한다.

인증 안 된 요청은 401, 로그인했지만 타인 자료이거나 존재하지 않는 자료는 동일하게 404로 응답한다. CSRF 실패는 403이다. 자료별 응답과 다운로드에는 `Cache-Control: no-store`를 적용하고 파일은 정적 디렉터리에 직접 공개하지 않는다. 음성/영상 Range·HEAD, SRT·검수 보고서·검증 자료도 같은 규칙을 적용한다. 매 요청과 파일 접근에 권한 검사를 적용한다. [OWASP 권한 검사 지침](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), 확인일 2026-11-17.

검증 자료 HTML을 같은 출처에서 임의 스크립트로 실행시키지 않는다. 첫 버전은 HTML 보고서를 다운로드용 첨부로 제공하거나 스크립트 없는 격리 정책을 적용하고, JSON·PNG·MP4 조회와 구분한다. 브라우저의 localStorage는 계정 전환 시 이전 작업 ID·결과를 제거한다. 로그인 복귀나 새로고침은 기존 작업을 조회할 뿐 새 작업을 생성하지 않는다.

다음 수치는 초기 제안이며 배포 전 정책으로 확정한다. 지금 기존 데이터나 파일을 삭제하지 않는다.

| 데이터 | 초기 정책안 |
|---|---|
| 새 원본·파생 음성·전사·검수·후보·검증 자료 | 원본 생성부터 7일, 동일 원본의 후속 분석은 기한을 자동 연장하지 않음 |
| 후보 출력·SRT | 부모 원본 기한을 상속. 단독 추출은 작업 생성부터 7일 |
| 토큰·SNS 연결 | 연결 유지 중 암호화 보관, 연결 해제·탈퇴 시 사용 차단과 자격 증명 정리 |
| 삭제 이력·최소 운영 기록 | 원문·제목·URL·이메일·토큰을 제거한 내부 ID·상태·시각만 30일 |
| 향후 운영 백업 | 최대 30일 보관을 제안. 백업 복구 시 삭제 표식을 먼저 적용해 자료 재노출 방지 |
| 기존 로컬 자료·평가 원본·CLI 산출물 | 자동 귀속·자동 삭제 제외. 명시적인 이전 대상 목록으로만 편입 |

원본 삭제는 해당 원본의 모든 분석·전사·검수·후보·출력·검증 자료를 대상으로 한다. 출력 하나만 삭제하면 공유하는 원본과 다른 출력은 보존한다. 서버가 관리하는 데이터 루트 안의 등록된 파일만 삭제하고, 사용자가 지정한 외부 원본 경로는 지우지 않는다. 경로 이탈·심볼릭 링크 이탈도 거부한다.

삭제 API는 접수 상태를 먼저 저장하고 비동기 정리한다. 동일 대상의 반복 접수는 같은 삭제 작업으로 돌려준다. 실제 파일·민감 DB 내용의 정리가 끝났을 때만 완료로 표시한다. 중간 실패는 실패 상태와 재실행 근거를 남기며 정리는 같은 대상을 반복 처리해도 결과가 달라지지 않도록 한다.

수동 자료 삭제는 관련 pending/queued/running 작업, 진행 중인 SNS 전송·상태 조회, unknown SNS 전송이 있으면 409로 거부한다. 자동 만료는 기한에 접근을 차단하고 정리를 보류한다. 기존 조회만 잠깐 허용해 만료를 숨기지 않는다. worker 선점·출력 확정·SNS 전송 시작과 삭제 접수는 같은 자원 잠금·상태 조건으로 직렬화한다. 먼저 실행을 시작한 작업은 파일을 사용하는 동안 정리 대상에서 제외하고, 삭제가 먼저 접수되면 늦은 대기열 메시지가 작업·외부 호출·파일을 생성하지 못하게 한다.

워커 중단으로 running이 남으면 자동으로 안전 종료됐다고 가정하지 않는다. 운영자가 실제 프로세스 종료와 외부 전송 상태를 확인할 때까지 정리를 보류한다. 이것은 삭제 안전을 위한 조치이며 업무 자동 재시도·자동 복구 구현과 구분한다. 파일 다운로드도 사용 중 표시를 두어 정리가 열린 파일과 경쟁하지 않게 하고, 이미 내려받은 파일을 원격 회수한다고 안내하지 않는다.

탈퇴는 최근 Google 재인증과 삭제 대상 미리보기를 거쳐 접수한다. 모든 앱 세션을 폐기하고 신규 작업·SNS 전송·자료 접근을 즉시 차단한다. 실행 중 외부 호출의 취소를 보장하지 않고 안전 종료 후 자료를 정리한다. 미확정 업로드가 남으면 탈퇴 정리도 보류 상태로 명시한다. 앱의 자료 삭제는 이미 YouTube에 올라간 영상 삭제를 포함하지 않으며, 외부 게시물의 처리 범위를 화면에서 구분한다. 이후 같은 Google 계정으로 가입해도 삭제한 자료가 재연결되지 않아야 한다.

## API와 화면 변경안

| 경로 | 계획한 동작 |
|---|---|
| GET /auth/google/start, GET /auth/google/callback | 일회성 Google 로그인 시작·결과 검증 |
| GET /auth/me, POST /auth/logout | 사용자·세션별 CSRF 정보 조회, 세션 폐기 |
| GET /assets, GET /jobs | 본인 자료·작업 목록과 만료 시각, 페이지 단위 조회 |
| DELETE /assets/{id}, DELETE /jobs/{id} | 삭제 범위 미리보기 후 접수, 202와 삭제 조회 URL 반환 |
| GET /deletions/{id} | 본인 삭제 작업 상태·보류/실패/완료 조회 |
| DELETE /auth/me | 재인증 확인 후 탈퇴·자료 삭제 접수 |

기존 업무 API의 경로·영상 처리 계약은 유지하면서 인증·소유권 의존성을 추가한다. 로그인 화면, 본인 자료 목록, 만료 안내, 삭제 범위 확인·처리 결과, 로그아웃·탈퇴 화면을 추가한다. 기존 전사·추천·검증·SNS 화면은 사용자 경계를 공유하게 한다. 재생 중 세션 만료는 로그인 안내로 처리하고 분석 재생성을 유도하지 않는다. health는 공개 최소 상태로 유지한다.

| AUTH-DATA-01 | users·identity·session·소유자·삭제 상태 migration과 기존 자료 이전 절차 | 신규/기존 DB migration 검사, 미귀속 자료 격리, dry-run 이전 목록 |
| AUTH-DATA-02 | Google 로그인·콜백·세션·로그아웃·공통 CSRF | 잘못된 state/nonce/서명/aud/만료·재사용 차단, 서버 로그아웃 후 세션 거부 |
| AUTH-DATA-03 | 전체 업무 API·파일·원본 재사용·SNS의 소유권 검사 | 사용자 A/B 교차 접근 전수 거부, 본인 흐름 정상, 타인 작업 SNS 연결 불가 |
| AUTH-DATA-04 | 본인 자료 목록·보관 기한·삭제 접수·정리·탈퇴 | 삭제 범위 일치, 진행 중 거부, 만료 차단, 중복/실패 후 정리 안전성 |
| AUTH-DATA-05 | 기존 브라우저 흐름 회귀·실제 인프라 통합·운영 문서 | 로그인부터 출력·재접속·로그아웃·삭제까지 통합 통과, 실계정 로그인 별도 확인 |

현재 진행 중인 작업을 이어서 변경하지 않도록 구현 착수 시 최신 기준 커밋과 migration 번호를 확인한다. 기존 미커밋 변경은 보존하며 인증 작업은 별도 브랜치/작업 공간에서 진행한다. 공통 수정 지점은 models, 모든 api, repositories, 워커 선점·완료, 웹 fetch와 SNS owner다. 번호는 현재 제안한 작업 분해이며 GitHub Issue 생성 사실을 뜻하지 않는다.

기존 데이터에 첫 로그인 사용자를 일괄 소유자로 지정하지 않는다. 먼저 소유자가 없는 기존 로컬 자료를 격리하고, 운영자가 선택한 대상만 dry-run·명시적 사용자 매핑 후 이전한다. 기존 SNS 계정·토큰은 첫 버전에서 로그인 후 재연결하게 하며 구 브라우저 쿠키만으로 소유권을 승격하지 않는다. 소유자 없는 행을 새 API에서 접근 불가로 만든 후 최종 제약을 강화한다. 전환 중 워커 쓰기를 멈추고 DB·파일 상태를 확인해 경합을 피한다.

인증 모드에서 구성·DB에 문제가 있으면 접근을 거부한다. 개발용 무인증 우회를 운영 환경에서 켤 수 없게 하고, 외부 공개 전 모든 업무 경로가 인증 모드에서만 동작하는지 검사한다. health·로그인 정적 화면 외 보호 대상 목록을 테스트와 연결한다.

## 검증 계획과 공개 조건

일반 CI는 Google·YouTube 대역을 사용해 외부 계정이나 유료 모델을 호출하지 않는다. 기본 `uv run python scripts/verify.py`와 PostgreSQL·Redis·Celery·FFmpeg·Chromium 격리 통합 검사를 수행한다. 특히 다음 시나리오를 회귀 검사로 남긴다.

- A/B 사용자로 모든 업무 경로·파일 Range·SRT·검증 자료·원본 재사용·후보 출력·SNS 확인/전송을 교차 검사한다. 응답 거부뿐 아니라 DB·파일·발행·외부 호출에 부작용이 없는지도 확인한다.
- 세션 위조·만료·폐기, 로그인 콜백 재사용·CSRF·임의 복귀 URL, 로그아웃/계정 전환 후 이전 자료 표시 여부를 검사한다.
- 삭제와 워커 선점·늦은 완료·외부 전송·다운로드의 경쟁을 실제 DB로 검사한다. 반복 정리·프로세스 중단·경로 이탈·일부 파일 유실도 포함한다.
- 탈퇴 중 재로그인·자료 재노출, 만료 직후 조회·출력·재사용, 삭제 완료 후 DB의 전사/URL/자격 증명 잔존 여부를 확인한다.
- 새로고침의 작업 재생성 방지·조회 통신 오류와 업무 실패 구분·중복 제출 방지·후보별 출력 재사용을 유지한다.

실제 Google 로그인은 준비된 테스트 계정·콜백 설정으로 별도 수동 검증한다. 실제 YouTube 게시나 사용자 자료 삭제는 이 계획 수립에 포함되지 않는다. 운영 도메인·백업·보관 정책이 확정되고 사용자 간 격리·삭제 검사가 통과하기 전에는 외부 공개 완료로 표현하지 않는다.

## 남은 결정

Google 로그인은 사용자 선택으로 확정했다. 7일 자료 보관·세션 기한·30일 최소 기록/백업은 제안이며 구현 단계에서 설정과 화면 안내를 함께 확정한다. 운영 도메인·로그인 클라이언트·테스트 계정, 백업 저장 위치와 복구 절차, OIDC 의존성은 착수 시 정한다. 법적 보관 의무나 준수 인증을 완료한 계획으로 표현하지 않는다.
